# CAT ドキュメント管理手順

作成日・適用開始日：2026-10-25

状態：合意済みの共通運用手順。適用対象はCATを扱う全チャット。①保存タイミング、②編集分担・競合、③履歴・識別、④配置・入口の合意を反映している。製品の正式REQ／SPECではなく、この手順の整備は製品実装の開始を意味しない。

## 1. 目的と適用範囲

**合意済みの範囲：** CAT専用の共通手順とする。チャットが変わっても、現在の決定、未決事項、調査根拠、更新先を確認できるようにする。

要件整理・調査・将来の仕様化や実装に伴う文書更新を対象とし、読み込み、記録、参照、変更確認、引継ぎの手順を定める。製品の挙動や性能値は各分野の文書で管理する。

既存の参照先：

- [共通の入口：AGENTS.md](../../AGENTS.md)
- [適用中の詳細な作業規則](../organize/下書き・参考/ドキュメント構成の参考.md)
- [要求工学・AI分業方針](../organize/下書き・参考/CAT_REQUIREMENTS_ENGINEERING_WORKFLOW.md)
- [整理3の索引](../organize/整理3.md)

## 2. 既存の合意・作業規則から引き継ぐ原則

- 現在は再構築の要件整理段階である。整理3の分割は、正式REQ／SPECへの移行や実装開始を意味しない。
- 決定事項、提案、未決事項、調査で確認した事実を区別する。調査結果やAIの提案を自動的に製品仕様へ採用しない。
- 整理3.mdは索引とし、詳細は整理3フォルダの分野別文書で管理する。同じ詳細を複数箇所へ複製して並行更新しない。
- 分割前の全文は固定された保存記録であり、現在の更新先として扱わない。
- 関係する文書を必要な範囲で読む。毎回すべての文書を読み込むことを要求しない。
- ユーザーの決定をAIが独断で変更しない。矛盾や未決事項は、その箇所と影響を明らかにする。
- 他の作業による変更や既存の調査資料を保持する。過去の調査対象版・確認日を、新しい文書更新日で上書きしない。
- 正式な要求・仕様・設計と要件整理資料の役割を分ける。旧実装を再構築後の仕様の根拠として自動採用しない。

## 4. 文書更新の手順

1. **対象を確認する。** 実際のプロジェクトの場所、今回の依頼、作業段階、関連文書を確認する。
2. **必要な箇所を読む。** 整理3の索引から対象分野と関連分野を確認する。調査が必要なら根拠の報告書を読む。
3. **記録内容を分類する。** 合意済みの変更、未承認の案、未決事項、調査事実を分ける。変更の根拠となるユーザーの決定や資料を追える形にする。
4. **影響先を確認する。** 更新する詳細本文に加え、共通規則、関連する要約、残課題、索引への影響を確認する。意味の異なる記述を単に同じ文言へ揃えない。
5. **編集直前の状態を確認して更新する。** 別の作業で対象箇所が変わっていれば、その変更を読み直す。意味に関わる競合は推測で統合しない。
6. **変更内容を確認する。** 意図した範囲の変更か、数値・条件・状態区分を変えていないか、参照や表示が壊れていないかを確認する。
7. **保存結果を伝える。** 更新した文書、反映した決定、未反映・未決の事項、実施した確認を簡潔に伝える。保存完了ごとに、この会話の残り作業・次の論点・調査待ちや範囲外の扱いも示す（[引継ぎ手引き2.2](会話引継ぎと開始の手引き.md#remaining-work)）。保存指示のターンは4.1節に従い推論レベルだけを回答し、実際の保存後に報告する。

保存のタイミングは以下の4.1節、複数チャットの編集分担と競合への基本対応は4.2節、変更履歴の粒度は4.3節、正式な入口の配置は4.4節に従う。

### 4.1 保存タイミングとコンテキスト圧縮への備え

**現行の合意（2026-11-02変更）：** ファイルへの保存・更新は利用者から明示的な指示がある場合に行う。ある程度まとまるまでは会話で整理し、論点への合意や質問への回答だけを保存指示とは解釈しない。2026-10-25の「個別の保存指示を待たずに反映する」運用は、この合意に置き換える。

- 2026-11-04変更：保存指示を受けたターンでは、作業に適した推論レベルの推奨だけを回答し、ファイルを変更せずにターンを終える。利用者が設定を変更できるよう、次のターンで「再開してください」「続けてください」等の再開指示を受けてから、指定範囲を保存して結果を報告する。明示的な文書編集依頼も対象範囲の保存指示として扱う。推奨を回答済みの保存について再開指示があれば、推奨のみのターンを繰り返さない。
- 議論の長期化や論点の区切りだけでは途中保存しない。合意済み事項・未決の論点・検討中の案を会話で区別し、保存指示を待つ。
- モード変更、圧縮が近いこと、利用者による圧縮・チャット移行の予告だけでは自動保存しない。必要な場合は未保存内容と再開地点を会話で簡潔に示す。毎回答で保存確認を求めない。
- 引継ぎの保存を指示された場合は、現在の論点、承認待ちの提案、未決事項・保留理由、残課題の順序、必要な参照先、次に行う作業を残す。詳細本文を引継ぎ欄へ重複して転記せず、保存先を示す。
- 保存できなかった場合は、保存済みと報告せず、未保存の範囲と理由を明示する。

**実行上の制約：** 自動圧縮の正確な発動時点を必ず事前検知できるとは確認されていない。この制約を理由に保存指示を省略しない。圧縮後は保存済み文書と利用可能な会話の要約を確認して再開し、未保存内容を保存済みと扱わず、不明な決定を推測で補わない。

### 4.2 複数チャットの編集分担と競合

**合意済み（2026-10-25）：** 異なる分野はそれぞれのチャットで更新できる。同じ箇所の変更が重なった場合は最新内容を読み直し、意味に関わる競合を勝手に上書きしない。

- 編集前に対象箇所の最新内容を確認し、以前読み込んだ内容だけを基に文書全体を上書きしない。
- 他の変更があれば、その内容と今回の変更の関係を確認する。競合する箇所は変更前後の内容と根拠を整理し、製品上の判断が必要な場合は利用者に確認する。
- 異なる分野の文書であっても、共通規則や責任分担に影響する変更は関連文書との整合を確認する。
- この運用は編集上の手順であり、ファイルの排他制御や他チャットの変更を自動検知する仕組みを導入したことを意味しない。

### 4.3 変更履歴と識別方法

**合意済み（2026-10-25）：** 次の粒度で、現行本文を読みやすく保ちつつ変更理由を追えるようにする。

- 意味に関わる決定・変更は、対象文書の短い変更履歴に「日付・対象の節・変更概要・理由または根拠」を記録する。会話全文は転記しない。
- 誤字やリンクだけの修正は、重要な決定履歴とは分けて扱う。コミット済みの変更はGit履歴も参照できるが、未コミットの内容がGit履歴に保存されているとは扱わない。コミット実施の方針は別途扱う。
- 現在の旧節番号とリンク用アンカーは維持し、移動・追加による一括振り直しや別項目への使い回しを避ける。今は正式なREQ／SPECのIDを付ける段階へ移行しない。
- 固定保存版は大きな分割・統合・段階移行などの節目で残し、通常更新のたびに全文コピーを増やさない。保存版は現行本文と並行更新しない。

### 4.4 正式な入口と適用開始

**合意済み（2026-10-25）：** docsフォルダ内の現行資料・参考・旧資料の整理を先に行い、以下の配置と役割分担で共通手順の運用を開始した。

- 本手順の確定先は `docs/workflow/ドキュメント管理手順.md` とする。読み込み・更新・保存・検証・引継ぎの詳細はここで管理する。
- ルートの `AGENTS.md` は短い入口とし、現在の作業段階、必須の基本規則、本手順と整理3の索引への参照を記載する。
- 現在適用している「ドキュメント構成の参考.md」の作業規則と「CAT_REQUIREMENTS_ENGINEERING_WORKFLOW.md」の要求策定方針は参照先として保持する。AGENTS.mdを短くするために既存の規則を暗黙に廃止しない。これらの全文移動・再編は別途扱う。
- 整理3の索引とdocsの入口からも本書を参照する。下書きの元の場所には本書への案内を残し、手順の全文を二重に更新しない。
- 手順は将来改良できるものとし、運用の意味が変わる提案は利用者との合意後に更新し、変更履歴へ理由を残す。

この手順を参照するCATの各チャットで合意済みの運用を実施する。全チャット共通の入口を整備しただけで、既に実行中の他チャットが直ちに再読したことまでは保証しない。

### 4.5 チャット移行と推論レベル（2026-11-01合意）

会話開始・再開、handoff作成・第三者確認・引継ぎ先初回確認では、必ず[会話引継ぎと開始の手引き](会話引継ぎと開始の手引き.md)を参照する（2026-11-04追加）。具体手順と必須記載事項の更新先は同手引きに一本化する。以下の移行原則・推論レベル、4.1の保存、4.6の影響評価は維持する。

2026-11-05変更：第三者確認は新チャットの最初のやり取りで確認問題への回答と併せて実施し、利用者が結果を旧チャットへ持ち帰って判定する。[手引き第3節](会話引継ぎと開始の手引き.md#independent-review)の確認者情報（取得可能なモデル名・実際の推論レベルと情報源／取得不可）と、[第5節](会話引継ぎと開始の手引き.md#initial-check)の持帰り判定に従う。旧チャット内での事前レビューは実績として残し、新方式の完了と区別する。

会話の目標・範囲案と利用者確認、終了条件、範囲完了後の関連事項の見直しは[手引き2.1](会話引継ぎと開始の手引き.md#conversation-scope)、保存完了ごとの残り作業提示は[2.2](会話引継ぎと開始の手引き.md#remaining-work)、移行ごとの連番・現在参照先の識別は[2.3](会話引継ぎと開始の手引き.md#handoff-numbering)に従う。対象ファイルは[handoff一覧](../organize/整理3/handoff/README.md#current)で確認する。

- 現在の合意・理由・保留・次の作業を文書から再現できる状態へ整理して、新しいAstraチャットへ移行する。未決の製品仕様を全て解決することは移行条件にしない。移行先で認識のずれを防ぐために必要な文書整理・確認は現在のチャットで行うが、ずれゼロを保証したとは報告しない。
- 移行前照合と今後の変更確認では、以下の4.6節の影響評価を暫定運用する。低影響で後回しにした他機能干渉は最終チェックへ残し、確認済みと扱わない。
- 通常の要件比較・判断支援はAstra Medium、更新文面と更新先が確定した機械的反映はLow、複数文書の意味統合・撤回案整理・責任分担照合はMedium、難しい矛盾や重要な整合確認は必要範囲でHighを推奨する。一律Lowにはせず、手戻りを含めて評価する。
- 保存指示のターンは推奨レベルと必要なら短い理由だけを回答し、実際の保存は4.1節に従って次の再開指示後に行う（2026-11-04変更）。推奨は作業内容に合わせる。案内だけで設定が切り替わった、またはその設定で実行されたとは報告しない。
- 30〜50ターンは移行を点検する目安とし、テーマの区切り・文脈の混乱・利用負担を踏まえて判断する。ターン数だけで強制移行せず、保存は4.1節に従い利用者の明示指示を受けて行う。

### 4.6 影響評価による照合の絞込み（2026-11-01暫定運用を承認）

目的は機能横断照合の優先順位付けであり、仕様の正しさ・実装可能性を採点するものではない。0〜3の4段階で、**2以上**をその場の関連照合対象とする。

| 影響度 | 目安 | 確認範囲 |
| --- | --- | --- |
| 0：意味の変更なし | 誤字・書式・リンク等。識別名や操作の意味を変えない | 変更箇所と参照 |
| 1：機能内に限定 | 他機能の入出力・実行条件・保存内容・権限を変えない | 対象機能内。他機能への低影響の干渉は最終チェック待ち |
| 2：機能間に影響 | 他機能が受け取る情報・受付条件・処理順・継承結果等が変わる | 直接の影響先と、その先の影響が疑われる箇所 |
| 3：共通の仕組みに影響 | 制御優先順位・責任分担・権限・識別・保存復元等を横断して変える | 関連共通規則と複数機能 |

- 各決定を一度は評価する。影響先が同じ関連決定はまとめて記録・照合してよいが、対象の決定を特定できるようにする。点数は加算・平均せず、該当する最も高い段階を採る。
- 記録は原則「決定／影響度／理由一文／影響先／照合状態」の1行。根拠の本文・節への参照を添え、評価済みと照合済みを区別する。
- 点数にかかわらず、①既知の矛盾・既決事項の撤回や上書き、②非常制御・停止保持・操作権限・データ消失防止の意味の変更、③影響先を判断できない場合は確認する。③は0ではなく未評価とし、分類に必要な範囲を先に確認する。
- 本文・索引・参照先の直接の更新確認は全件行う。省くのは低影響事項の広い機能横断照合であり、必要な更新を省略する規則ではない。
- 照合済みの決定は関連前提・仕様が変わらない限り毎回読み直さない。後回し分は「最終チェック待ち」、影響を絞っただけなら「評価済み・照合待ち」と記録する。未確認を完了へ変えない。
- 少数の既存決定で分類を試してから移行前照合へ進む。分類に迷う場合や反例が出た場合は暫定基準を見直す。新しい製品判断を採点作業に混ぜない。

## 5. 更新の種類に応じた確認

| 更新の種類 | 主な確認 |
| --- | --- |
| 表記修正や小さな追記 | 変更差分、意味の保持、関連リンク |
| 合意による要件変更 | 変更前後の条件、関連機能との整合、古い記述や残課題の更新漏れ |
| 調査結果の追加 | 出典・対象版・事実と考察の区別、未検証範囲、採用未決の明示 |
| 移動・分割・統合 | 元資料の保持、欠落・重複、移行先、参照先、内容を変えない範囲の照合 |
| 他チャットへの引継ぎ | 対象範囲、合意済み事項、未決事項、関連文書、次に行う作業 |

2026-10-25の分割検証は、その時点の移行が元文書の内容を保持したことを確認する記録である。後日の承認済み変更まで分割前と一致させるための制約として扱わない。固定保存版は4.3節の節目で残す運用とし、通常更新では今回の変更範囲に応じて確認する。

## 6. 整備状況と今後の扱い

1. **保存タイミング（2026-11-02変更）**：4.1節のとおり、ある程度まとまるまでは会話で整理し、利用者の明示指示を受けて保存する。
2. **他チャットとの分担と競合（基本方針は合意済み）**：4.2節のとおり、異なる分野はそれぞれ更新でき、同じ箇所の意味に関わる競合は勝手に上書きしない。
3. **履歴と識別方法（合意済み）**：4.3節のとおり、短い決定履歴、旧節番号・リンクの維持、節目の固定保存版を用いる。Gitのコミット実施方針は別途扱う。
4. **正式な入口と適用開始（整備済み）**：4.4節のとおり、docs整理後に本書とAGENTS.mdを配置し、索引から参照できるようにした。

[docsの入口](../README.md)と[文書台帳](../文書台帳.md)で現在の文書の所在と旧資料の注意点を確認できる。製品要件の再開地点は[整理3の索引](../organize/整理3.md)と残課題の文書で管理する。Gitのコミット実施方針と、既存の詳しい作業規則の全文再編は別途扱い、未決の方針を推測で補わない。
