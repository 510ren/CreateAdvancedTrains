# CAT ドキュメント管理手順 — 下書き

作成日：2026-10-25

状態：共同検討中。適用対象はCATを扱う全チャット。既存の合意・作業規則を参照し、文書管理の具体的な運用を相談するための下書きである。未承認の運用案を、このファイルを読んだことだけで必須の規則として扱わない。

## 1. 目的と適用範囲

**合意済みの範囲：** CAT専用の共通手順とする。チャットが変わっても、現在の決定、未決事項、調査根拠、更新先を確認できるようにする。

**構成案：** 要件整理・調査・将来の仕様化や実装に伴う文書更新を対象とし、読み込み、記録、参照、変更確認、引継ぎの手順を定める。製品の挙動や性能値は各分野の文書で管理する。

既存の参照先：

- [作業規則として適用中の下書き](ドキュメント構成の参考.md)
- [要求工学・AI分業方針](CAT_REQUIREMENTS_ENGINEERING_WORKFLOW.md)
- [整理3の索引](../整理3.md)

## 2. 既存の合意・作業規則から引き継ぐ原則

- 現在は再構築の要件整理段階である。整理3の分割は、正式REQ／SPECへの移行や実装開始を意味しない。
- 決定事項、提案、未決事項、調査で確認した事実を区別する。調査結果やAIの提案を自動的に製品仕様へ採用しない。
- 整理3.mdは索引とし、詳細は整理3フォルダの分野別文書で管理する。同じ詳細を複数箇所へ複製して並行更新しない。
- 分割前の全文は固定された保存記録であり、現在の更新先として扱わない。
- 関係する文書を必要な範囲で読む。毎回すべての文書を読み込むことを要求しない。
- ユーザーの決定をAIが独断で変更しない。矛盾や未決事項は、その箇所と影響を明らかにする。
- 他の作業による変更や既存の調査資料を保持する。過去の調査対象版・確認日を、新しい文書更新日で上書きしない。
- 正式な要求・仕様・設計と要件整理資料の役割を分ける。旧実装を再構築後の仕様の根拠として自動採用しない。

## 4. 文書更新の手順案

1. **対象を確認する。** 実際のプロジェクトの場所、今回の依頼、作業段階、関連文書を確認する。
2. **必要な箇所を読む。** 整理3の索引から対象分野と関連分野を確認する。調査が必要なら根拠の報告書を読む。
3. **記録内容を分類する。** 合意済みの変更、未承認の案、未決事項、調査事実を分ける。変更の根拠となるユーザーの決定や資料を追える形にする。
4. **影響先を確認する。** 更新する詳細本文に加え、共通規則、関連する要約、残課題、索引への影響を確認する。意味の異なる記述を単に同じ文言へ揃えない。
5. **編集直前の状態を確認して更新する。** 別の作業で対象箇所が変わっていれば、その変更を読み直す。意味に関わる競合は推測で統合しない。
6. **変更内容を確認する。** 意図した範囲の変更か、数値・条件・状態区分を変えていないか、参照や表示が壊れていないかを確認する。
7. **保存結果を伝える。** 更新した文書、反映した決定、未反映・未決の事項、実施した確認を簡潔に伝える。

保存のタイミングは以下の4.1節、複数チャットの編集分担と競合への基本対応は4.2節、変更履歴の粒度は4.3節、正式な入口の配置方針は4.4節で合意済みとする。docs内の整理を先行した後、正式配置を行う。

### 4.1 保存タイミングとコンテキスト圧縮への備え

**合意済み（2026-10-25）：** 関連する論点のまとまりが合意された時点で、利用者からの個別の保存指示を待たずに文書へ反映する。短い確認のたびに全文を更新する必要はない。コンテキストの自動圧縮が入る前に保存することを運用上の目標とし、圧縮直前まで未保存の内容を溜めない。

- 通常は話題の区切りで保存し、保存先と変更内容を簡潔に報告する。
- 議論が長くなる場合は、区切りの完成を待たずに途中保存する。合意済み事項は関連する本文へ、未決の論点や検討中の案は状態を明示して記録する。
- 圧縮が近いことを把握できた場合や、利用者が圧縮を行う旨を伝えた場合は、次の検討へ進む前に未保存内容と再開地点を保存する。
- 再開用には、現在の論点、承認待ちの提案、未決事項・保留理由、残課題の順序、必要な参照先、次に行う作業を残す。詳細本文を引継ぎ欄へ重複して転記せず、保存先を示す。
- 保存できなかった場合は、保存済みと報告せず、未保存の範囲と理由を明示する。

**実行上の制約：** このチャットで利用できる手段から、自動圧縮の正確な発動時点を必ず事前検知したり、圧縮直前に必ず保存処理を挟んだりできることは確認できていない。したがって「直前の検知」を唯一の保存契機とせず、通常のこまめな保存と早めの途中保存で備える。圧縮後は保存済み文書を確認して再開し、不明な決定を推測で補わない。

### 4.2 複数チャットの編集分担と競合

**合意済み（2026-10-25）：** 異なる分野はそれぞれのチャットで更新できる。同じ箇所の変更が重なった場合は最新内容を読み直し、意味に関わる競合を勝手に上書きしない。

- 編集前に対象箇所の最新内容を確認し、以前読み込んだ内容だけを基に文書全体を上書きしない。
- 他の変更があれば、その内容と今回の変更の関係を確認する。競合する箇所は変更前後の内容と根拠を整理し、製品上の判断が必要な場合は利用者に確認する。
- 異なる分野の文書であっても、共通規則や責任分担に影響する変更は関連文書との整合を確認する。
- この運用は編集上の手順であり、ファイルの排他制御や他チャットの変更を自動検知する仕組みを導入したことを意味しない。

### 4.3 変更履歴と識別方法

**合意済み（2026-10-25）：** 次の粒度で、現行本文を読みやすく保ちつつ変更理由を追えるようにする。

- 意味に関わる決定・変更は、対象文書の短い変更履歴に「日付・対象の節・変更概要・理由または根拠」を記録する。会話全文は転記しない。
- 誤字やリンクだけの修正は、重要な決定履歴とは分けて扱う。コミット済みの変更はGit履歴も参照できるが、未コミットの内容がGit履歴に保存されているとは扱わない。コミット実施の方針は別途扱う。
- 現在の旧節番号とリンク用アンカーは維持し、移動・追加による一括振り直しや別項目への使い回しを避ける。今は正式なREQ／SPECのIDを付ける段階へ移行しない。
- 固定保存版は大きな分割・統合・段階移行などの節目で残し、通常更新のたびに全文コピーを増やさない。保存版は現行本文と並行更新しない。

### 4.4 正式な入口と適用開始

**合意済み（2026-10-25）：** 以下の配置と役割分担で共通手順を利用する。ただし利用者の追加指示により、AGENTS.mdなどの整備前にdocsフォルダ内の現行資料・再利用可能な参考・旧資料を整理する。

- 本手順の確定先は `docs/workflow/ドキュメント管理手順.md` とする。読み込み・更新・保存・検証・引継ぎの詳細はここで管理する。
- ルートの `AGENTS.md` は短い入口とし、現在の作業段階、必須の基本規則、本手順と整理3の索引への参照を記載する。
- 現在適用している「ドキュメント構成の参考.md」の作業規則と「CAT_REQUIREMENTS_ENGINEERING_WORKFLOW.md」の要求策定方針は参照先として保持する。AGENTS.mdを短くするために既存の規則を暗黙に廃止しない。これらの全文移動・再編は別途扱う。
- 共通手順の確定時に、整理3の索引からも参照できるようにする。本下書きの元の場所には確定先への案内を残し、手順の全文を二重に更新しない。
- 手順は将来改良できるものとし、運用の意味が変わる提案は利用者との合意後に更新し、変更履歴へ理由を残す。

①～③で合意した運用は本チャットで実施する。全チャット共通の入口を整備しただけで、既に実行中の他チャットが直ちに再読したことまでは保証しない。

## 5. 更新の種類に応じた確認案

| 更新の種類 | 主な確認 |
| --- | --- |
| 表記修正や小さな追記 | 変更差分、意味の保持、関連リンク |
| 合意による要件変更 | 変更前後の条件、関連機能との整合、古い記述や残課題の更新漏れ |
| 調査結果の追加 | 出典・対象版・事実と考察の区別、未検証範囲、採用未決の明示 |
| 移動・分割・統合 | 元資料の保持、欠落・重複、移行先、参照先、内容を変えない範囲の照合 |
| 他チャットへの引継ぎ | 対象範囲、合意済み事項、未決事項、関連文書、次に行う作業 |

2026-10-25の分割検証は、その時点の移行が元文書の内容を保持したことを確認する記録である。後日の承認済み変更まで分割前と一致させるための制約として扱わない。固定保存版は4.3節の節目で残す運用とし、通常更新では今回の変更範囲に応じて確認する。

## 6. これから決める運用

1. **保存タイミング（合意済み）**：4.1節のとおり、論点のまとまりごとの保存と圧縮前に備えた早めの途中保存を行う。
2. **他チャットとの分担と競合（基本方針は合意済み）**：4.2節のとおり、異なる分野はそれぞれ更新でき、同じ箇所の意味に関わる競合は勝手に上書きしない。
3. **履歴と識別方法（合意済み）**：4.3節のとおり、短い決定履歴、旧節番号・リンクの維持、節目の固定保存版を用いる。Gitのコミット実施方針は別途扱う。
4. **正式な入口と適用開始（配置方針は合意済み・整備待ち）**：4.4節のとおり配置する。docs内の整理を先行し、AGENTS.md等はその後に整備する。

現在はdocs内の資料整理を優先する。[docsの入口](../../README.md)と[文書台帳](../../文書台帳.md)で整理結果と旧資料の注意点を確認できる。次に④の正式配置・入口整備へ戻る。製品要件の議論は、その後に保存ダイヤの管理と適用から再開する。
