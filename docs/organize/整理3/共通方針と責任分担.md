## 3. 機能の責任分担

<a id="u-3-1"></a>

### 決定

| 要素 | 責任 |
| --- | --- |
| ATO・ATACS・TASCなど | 担当する判断・計算を行い、共有する状態・結果をINTEROSへ渡す |
| INTEROS | 列車情報の正本、操縦指令の受付・検証・競合調整・確定、EB／保持理由の個別管理、情報共有・通知集約を担う |
| マスコン | 操作受付とHUD表示。表示情報はINTEROSから取得する。独自に列車制御計算・情報管理を引き受けない |
| ATOS | 常時動作し、INTEROS経由で情報を確認・共有し、プレイヤーによる遠隔操作要求を伝達する。現段階では自律的な運行操作を行わない |
| 共通の進路管理機能 | サーバー側で申請・占有・競合・既存許可・待機優先度を確認し、許可・待機・拒否を決める。マスコンやATOが独自に許可を確定しない |
| 地上信号 | 共通管理で確定した進路状態と先の区間条件に基づき、列車共通の現示を決める |

- 従来の「ATACSがD-ATCとATSを統合し、一括ON/OFFする」という定義は、[第3.1節](信号と安全装置と進路.md#s-3-1)の方式選択に伴う見直し対象。旧構成の内部Controller分担・名称を新方式へ自動継承しない。
- INTEROSの指令検証・権限管理などの基盤は無効化不可。ドア連動転動防止だけはServer Configで無効化できる（[第3.4節](乗務員とドアと停車保持.md#s-3-4)）。内部機能の総称であり、独立搭載機器の追加を意味しない。
- ATO中は必要な安全・操縦機能を個別OFFにできない。ただしTASCはATOの構成要素にせず、ATOが単独で停止位置制御・保持を行う。TASCのON／OFFに依存せず、ATO中に重ねて介入させない。その他の強制有効対象の完全な一覧は未決定。
- 手動時の安全機能OFFは[第3.3節](信号と安全装置と進路.md#s-3-3)の条件内で運転者の責任により許容する。ノッチ・前後切替などの基本操作機能は無効化不可とする方向だが、完全な対象一覧は未決定。

### 3.2 INTEROSによる操縦指令の一元管理（決定）

- マスコン・ATOS・時刻表・ATO・TASC・安全装置はINTEROSへ要求を渡し、列車の制御状態を直接書き換えない。走行・停止位置制御と各機能由来の保持は担当を分け、ドア連動転動防止は独立してINTEROSが担う。最終指令の調整・適用はINTEROSへ集約する（[第3.4節](乗務員とドアと停車保持.md#s-3-4)）。
- INTEROSはサーバー側で、適用直前の操作権・インターロック・非常状態・要求競合を確認し、採用する指定状態と実効指令を確定する。内部機能の要求も検証を迂回しない。
- 各マスコンの指定位置と列車に適用する指令を分離する。「指定P・実効EB」は正常な介入状態であり、不正な組合せではない。操作拒否時は元の位置を保持し、理由を返す。
- EB／停車保持理由は個別管理し、一つの要求の解除で他の理由を消さない。通常の指定EBも、その指定が制御に採用されている間の保持理由となる。ATOが無視する保存EBは別扱い。TASCは指定EBのまま自動停止を再開しない。
- 単なる手動停止や駅停車だけを理由にドア連動保持を開始しない。ATO・TASC引継ぎ等の要求とドア連動保持を別に管理し、一つを終了しても他の保持・非常理由を消さない（[第3.4節](乗務員とドアと停車保持.md#s-3-4)）。
- 使用中の台の不正状態は要復旧EB、未使用台は台単位で使用不可・要復旧とする（[第11.13節](マスコン操作とHUD.md#s-11-13)）。具体的なクラス・API設計は後の工程。

- INTEROSとATOは列車単位で管理し、主副それぞれに独立した運行状態を作らない。進捗・出力・EB理由・保持を共有し、台別には位置・向き・キー・HUD占有等を持つ。使用台と手動操縦担当は列車全体で一つに確定する。
- 反対側のHUDにも同じ「ATO動作中」等を表示する。閲覧だけでは操作権を移さず、列車単位ATOでも使用台のキー条件は維持する。
- 競合する通常操作はサーバーで先に検証・確定した操作を優先し、後続は確定後の状態で再検証する。クライアントの表示時刻を優先根拠にしない。手動取得が先ならATO折返しへ入らず、折返し開始が先なら取得を拒否する。操作の一部分だけを双方で確定させない。
- 安全要求・非常原因追加を通常操作の先着順で排除しない。原子的な確定範囲・全イベントの境界は後で設計する。

### 8.15 INTEROSによる通知（決定）

- 信号停止等を除く長時間待機をチャットで知らせる。正常な終着・指定なしの運行完了は対象外。通知対象理由の完全な一覧・具体的な文言は未決定。
- 各機能は理由の発生・更新・解消と通知要請をINTEROSへ渡す。Minecraftへ直接送信せず、各機能独自に再通知タイマーを持たない。
- INTEROSが列車単位で要請をまとめ、通知対象の複数理由を1件に併記する。長時間待機判定時間と再通知間隔は別に管理し、具体値は全体整理後に決める。
- 送信間隔はINTEROSが独立管理する。同じ理由の更新や新規要請で送信を前倒し・先送り・計時リセットしない。新理由は自身の通知条件成立後に次の送信へ含める。
- 対象理由が残れば定期送信し、全部解消すれば終了する。信号待ち等の対象外理由だけが残った場合も終了する。
- 通知先は列車の組立者を基本とし、一部の通知は現在の運転手にも送る。運転手とは有効なマスコンで操縦担当を取得したプレイヤーで、乗客・閲覧者ではない。同一人物へ二重送信しない。
- 共通キーに所有者を持たせないため「キー所有者と組立者へ通知する」という以前の案は廃止。ATO切替・運転エラー・選択要求等は運転手向け候補だが、宛先の完全な対応表は未決定。
- 各送信時にオンラインの対象者へ送る。未配信を保存・まとめ配信しない。ログイン時も待機が続いていれば次の定期送信で届く。
- 重大度による即時通知・間隔例外は別の検討項目。今回の長時間待機では要請追加を重大度変化とみなさない。ATO切替の即時通知、キー取り外し忘れ音は、それぞれ決定済みの個別通知。

### 13.16 CAT本体の目的・基本利用範囲・外部連携との分担（方針決定）

今回の会話で個別に承認された方針を記録する。本体に含める責任範囲、初回リリースの範囲、実装方式、技術的成立性は別であり、今回の承認を実装開始の許可としない。

**中心目的と中核機能**

- 中心目的：Createの鉄道に、車両性能に基づく運転操作・保安装置・自動運転・運行管理を、一貫した仕組みとして追加する。
- 運転操作と車両制御：マスコン、操作権限、プロファイルに基づく性能、INTEROSによる指令管理を本体の中核とする。
- 保安と自動運転：ATACS／ATS-P、ATO、TASCと、各機能の介入・復旧・引継ぎを本体の中核とする。
- 運行管理と情報提供：時刻表、進路・停車目標、ATOSからの要求、各機能が参照する運行状態を本体の中核とする。ATOSの非自律操作など、既存の責任分担は維持する。

**既存アドオンとの比較基準**

1. 必要な動作を満たすか。機能名や外観だけでなく、操作・状態・異常時の扱いまで比較する。
2. CATの独自性・独創性、すなわち「その機能がCATにあるべき利用上の理由」があるか。単に他MODと異なることを目的にしない。マスコン・INTEROS・時刻表との一体化、CAT固有の情報を使う動作、操作・設定・異常表示の統一、目指す運転体験への必要性を評価する。
3. 独自の価値を連携だけで実現できるか。可能なら連携を有力候補とし、不足するならCAT側の補完または独自実装を比較する。独自性があることだけで全面的な作り直しを必須にしない。
4. 対応版、更新追従、競合、保守、利用者の導入負担が妥当か。公開機能・対応表記と実機互換の証拠は区別する。

似た機能が存在するだけで既存合意を削除しない。表示・音響・外観も一律に本体から外さず、利用価値と連携の深さから個別に判断する。本体に含めても実装時期を後にできる。

**Create＋CATだけで成立させる基本的な利用範囲**

- Create自体が必要とする前提MODは別として、任意の鉄道アドオンを追加しなくても次の利用が成立することを目指す。
  - CAT列車の組立とプロファイル設定。
  - マスコンによる手動運転、必要な計器・警告の確認。
  - CATの信号・標識などを使った、選択した保安装置の利用。
  - 時刻表の設定とATO運行。
  - ドア付き車両での運転手・車掌またはワンマンによる基本的な開閉操作。
  - 特別な車両モデルを導入しない、Createの通常の車両構成での上記利用。
- 任意アドオンがないときは対応する連携機能を利用不可とし、基本の運転・保安・運行管理まで利用不能にしない。
- これはCAT本体として目指す利用範囲であり、初回リリースへ全項目を含める決定ではない。自由デザインLCD、高度な車両音響、汎用的な車内移動改善は、この基本成立条件とは分ける。

**分野別に承認された責任範囲**

**別MOD化とCAT Lib**

- 別MOD化は、CATなしでも独立した利用価値があり、分離してもCATの基本利用範囲を損なわない機能を候補とする。汎用着席復元やモデル表示は例であり、分離決定ではない。
- CAT Libは複数のMODで共通して必要になる具体的な処理・利用先が見えてから検討する。コード量の多さだけでは作成しない。
- 本体内部で機能を整理することと、配布するMODを分割することは別。内部の分割は追加MODの導入を必須にする理由にならない。
- 将来ライブラリを分離する場合もCreate＋CATの基本導入方針との整合を確認し、実装都合だけで別途導入が必要な依存MODを増やさない。個別の別MOD化、CAT Libの作成／配布方式、CAT名称の変更は未決定。

**旅客向け表示の本体提供（追加承認）**

- 基本的な車内LCDと駅の電光掲示板をCAT本体で提供する。設置を運行の必須条件にはせず、初回リリースの搭載時期は別に決める。
- 自由度の高いデザイン・多彩な表示機器は追加機能・既存アドオン連携も比較する。基本表示の決定は[第13.17節](LCDと旅客案内.md#s-13-17)、保存ダイヤ・延発の追加は[第8.29・8.30節](分割記録/節の対応表.md#s-8-29)。
- 従来の残課題①～⑥、途中のドア議論、線路97候補・電力詳細の保留を維持する。次は[第1.5節](共通方針と責任分担.md#s-1-5)の方式で保存ダイヤの残課題をまとめる。
