# AGENTS.md

This file defines the mandatory working rules for AI agents operating in this repository.

These rules apply to all models and agents unless the user explicitly overrides them for the current task.

This file defines workflow and authority boundaries. Product requirements, architecture, design decisions, and coding standards are maintained in the relevant documents under `docs/`.

---

## 1. Source of Truth

CAT is being redesigned from the ground up.

Do not assume that requirements, architecture, design decisions, implementation patterns, or behavior from an earlier version of CAT remain valid.

Only information explicitly approved for the current redesign should be treated as authoritative.

Approved project documentation under `docs/` is the primary source of truth for the project.

Historical code may be inspected when useful, but its behavior must not automatically be treated as a current requirement or design decision.

---

## 2. Read Only the Relevant Project Documents

Before performing substantial requirements, design, planning, investigation, or implementation work, determine which project documents are relevant to the current task and read them.

Do not automatically load or review every document in `docs/`.

Read only the documents required to understand the current subject accurately.

Relevant documents may include, depending on the task:

* `docs/project/`
* `docs/requirements/`
* `docs/architecture/`
* `docs/design/`
* `docs/standards/`
* `docs/decisions/`
* `docs/workflow/`
* `docs/phases/`
* relevant files under `vendor/`

For example:

* requirements work should primarily consult relevant requirements and project-scope documents;
* architecture work should consult approved requirements and relevant architecture documents;
* implementation planning should consult the approved requirements, design, architecture, coding standards, and relevant source code;
* implementation should consult only the approved specifications and standards relevant to that implementation.

If another document becomes relevant during the task, read it when needed.

Do not rely on chat history as the sole source of an approved project decision when an authoritative project document exists.

---

## 3. User Authority

The user has final authority over:

* requirements,
* scope,
* architecture,
* design,
* behavior,
* compatibility decisions,
* coding policies,
* project conventions,
* implementation scope.

Agents may identify problems, propose solutions, compare alternatives, and make recommendations.

Agents must not independently finalize an unresolved requirement or design decision.

If a decision affects project behavior or design, either:

1. ask the user to decide, or
2. present a proposed choice and request approval.

A technically obvious solution is still not automatically an approved project decision.

---

## 4. Requirements and Design Work

When performing requirements or design work, actively identify relevant:

* missing requirements,
* ambiguities,
* contradictions,
* dependencies,
* boundary conditions,
* failure cases,
* states and transitions,
* interfaces,
* configuration requirements,
* compatibility constraints,
* technical risks,
* unresolved implementation dependencies.

Do not merely rewrite the user's statements.

Ask questions proactively when additional information is required.

Recommendations are allowed, but must remain clearly distinguishable from approved decisions.

Do not begin implementation during requirements or design work unless implementation has been explicitly authorized.

---

## 5. One Chat, One Primary Subject

Each chat should focus on one primary subject.

A subject may be:

* one feature,
* one phase,
* one bug,
* one subsystem,
* one investigation,
* one implementation task.

Avoid handling multiple substantially independent issues in the same chat.

If a separate issue is discovered:

1. identify it,
2. explain its relationship to the current task,
3. preserve enough context for continuation,
4. recommend handling it in a separate chat.

Do not substantially investigate or solve that separate issue in the current chat unless the user explicitly requests it.

---

## 6. Separate Requirements and Implementation When Appropriate

For substantial features, requirements/design work and implementation should normally use separate chats.

The requirements/design chat may contain exploration, rejected proposals, unresolved alternatives, and discussion history.

Before implementation, confirmed decisions should be written into the relevant project documentation.

The implementation chat should use those approved documents as its primary input instead of treating the entire previous discussion as authoritative.

Small, mechanically straightforward changes may remain within one chat when separation would provide little practical benefit.

---

## 7. Planning Before Implementation

Substantial implementation work should be planned before code is modified.

When Plan Mode or an equivalent planning workflow is available, use it before implementation.

Planning should determine, as relevant:

* exact implementation scope,
* affected components,
* required source investigation,
* applicable specifications,
* applicable coding and design standards,
* dependencies,
* implementation sequence,
* unresolved blockers,
* expected files to modify,
* significant implementation risks.

At the end of planning, provide a recommendation for:

* the most appropriate available model, and
* the most appropriate reasoning level

for the implementation task.

Base the recommendation on the actual complexity of the task rather than on a permanent model-specific role.

The user may change the model or reasoning level before implementation begins.

---

## 8. Implementation Requires Explicit Authorization

Do not modify project implementation code unless the user has explicitly authorized implementation for the current task.

Approval of:

* a requirement,
* a design,
* an architecture,
* a proposal,
* or an implementation plan

does not by itself authorize implementation.

If implementation is the logical next step but has not been explicitly authorized, request approval.

After authorization, remain within the approved implementation scope.

Do not add unrelated refactors, cleanup, features, or bug fixes unless they are required for the approved task or separately authorized.

---

## 9. Local Source Investigation

Agents may inspect:

* CAT source code,
* project documentation,
* locally available dependencies,
* source code placed under `vendor/`.

Do not use the internet to retrieve or inspect external project, dependency, library, mod, or API source code.

If additional source code is necessary:

1. identify what source is required,
2. explain why it is required,
3. ask the user to provide it,
4. expect it to be placed under `vendor/` or another explicitly agreed local location.

Do not guess implementation details that can reasonably be verified from source.

---

## 10. `vendor/` Is Reference Material

Files under `vendor/` are external reference material unless explicitly stated otherwise.

Do not modify, reformat, refactor, or treat vendored code as CAT-owned implementation code unless explicitly instructed.

Use vendored sources to verify external implementation behavior when relevant.

---

## 11. Build and Runtime Verification

Do not automatically perform time-consuming verification after implementation.

Unless explicitly requested, do not run:

* Gradle builds,
* dependency-resolution tests,
* Minecraft launches,
* integration tests,
* compatibility tests,
* repeated build/fix/build cycles.

Static inspection of edited code is allowed.

If automated verification appears particularly important, explain why and request authorization before running it.

Runtime and integration testing are normally performed by the user.

When useful, provide concise reproduction steps, expected behavior, and the information the user should report back.

---

## 12. Project Standards

Before implementation, consult the relevant approved documents under:

* `docs/architecture/`
* `docs/design/`
* `docs/standards/`

Follow applicable:

* architecture rules,
* design principles,
* module boundaries,
* dependency policies,
* coding standards,
* naming conventions,
* package conventions,
* documentation conventions,
* logging conventions,
* compatibility policies.

Do not invent new project-wide conventions during an isolated implementation task.

If an existing standard is insufficient or unsuitable, raise the issue for user approval before establishing a new convention.

---

## 13. Approved Decisions vs Proposals

Keep these categories distinct:

**Fact**
Something verified from authoritative project material, local source code, or provided external source.

**Proposal**
A possible requirement, design, architecture, or implementation approach that has not yet been approved.

**Decision**
A choice explicitly approved by the user and reflected in, or intended to be reflected in, authoritative project documentation.

Do not present proposals as decisions.

Do not present assumptions as facts.

---

## 14. Specification Completeness

Do not consider a substantial feature or phase specification complete merely because its general behavior has been discussed.

Before declaring it complete, verify that all relevant implementation-blocking questions have been resolved, including where applicable:

* purpose,
* normal behavior,
* important edge cases,
* important failure behavior,
* dependencies,
* required state and data,
* configuration,
* external interfaces,
* technical feasibility,
* unresolved technical dependencies.

If important unresolved items remain, identify them explicitly.

---

## 15. Documentation Maintenance

Authoritative project documents should describe the current approved state of the redesign.

Do not mix rejected proposals or obsolete design ideas into normative specification text without clearly marking their status.

When an approved decision changes, update or identify all affected authoritative documents.

Project documentation should be usable by a new implementation chat without requiring the full discussion history to reconstruct the intended behavior.

---

## 16. Conflicts Between Instructions and Specifications

Approved specifications are the primary authority for CAT's intended product behavior and technical requirements.

This `AGENTS.md` primarily governs agent workflow, authorization, source handling, and working procedure.

If `AGENTS.md` and an approved specification appear to conflict, do not silently choose either one.

Instead:

1. identify the conflicting statements,
2. explain the consequence of following each,
3. determine whether the conflict is caused by different scopes, ambiguity, outdated information, or genuine incompatibility,
4. present the comparison to the user,
5. ask the user which should apply.

If the user's current request conflicts with an approved specification, identify the conflict before treating the specification as changed.

A specification is not considered changed until the user confirms the intended change.

---

## 17. Model Independence

Do not assign permanent responsibilities based on model name.

Any suitable model may perform:

* requirements work,
* architecture work,
* design,
* investigation,
* planning,
* implementation,
* debugging.

Model and reasoning-level selection should be made per task.

The model used for requirements or planning does not need to be the model used for implementation.
