# 14. ワールド再開・再接続時の着席復元の調査

調査日：2026-10-22（日本時間）  
対象：Minecraft 1.20.1向けに提供されたCreate 6.0.8ソースと整理3.md、ユーザーの現象報告。  
検証：静的調査のみ。セーブデータ・ログの取得、Minecraft／Essentialでの再現、修正実装は未実施。

## 1. 要点と分類

**標準Createに乗客の保存・復元処理は存在するが、それを通常のログアウト／再ログインの座席復元保証とみなせない。** 鉄道管理のログアウト処理は空で、ログイン処理は線路・列車情報の同期を行う。さらに車両の乗客復元には、プレイヤーがまだオンラインでない場合に候補を消費し得る分岐がある。[C1,C2]

これは調べるべき接続上の候補であり、ユーザーの現象の原因を確定したものではない。Minecraft／Forge側のプレイヤー保存順、乗降イベント、実際の保存内容と突き合わせる必要がある。

- **利用者報告**：ユーザーが確認した現象。こちらで再現済みという意味ではない。
- **ソース事実**：提供コピーに存在する処理。
- **仮説／考察**：条件付きの原因候補・設計比較。未承認。
- **不明**：現象の確定原因と実際の保存・再接続順序。未確認事項を正常動作や既知の不具合として補わない。
- **[再調査:CAT]**：CAT仕様変更で照合し直す事項。
- **[再調査:依存版]**：Create等の対象版変更で読み直す事項。
- **[再調査:実機]**：実環境での再現・保存順・同期の確認が必要な事項。

| 列車状態 | 走行中・停止中の両方 |

**未確認**：実際のMinecraft／Create／Forge／Essentialの版、ホスト本人か参加者か、終了操作、停車列車が後に発車する条件、再現率。調査対象コードが6.0.8であることと、現象発生時の実行版が6.0.8であることは同一視しない。Essential固有の不具合とは判定できない。

## 3. 提供ソースで確認できたこと [再調査:依存版]

### 3.1 ログイン・ログアウト

`CommonEvents.playerLoggedIn`／`playerLoggedOut` は鉄道管理へ通知する。`GlobalRailwayManager.playerLogin()` は線路データを読み、グラフ・信号区間・列車パケットをプレイヤーへ送る。`playerLogout()` は空メソッドである。この二つのメソッドには座席の記録・再搭乗要求はない。[C1]

**限界**：この事実は、Minecraft標準や別の処理による保存まで存在しない証拠ではない。

### 3.2 保存には座席と乗客の二つの情報がある

`Carriage.write()` は、現在存在する車両実体の乗客を座席マッピングに対応付けてシリアライズし、既存の `serialisedPassengers` と合わせて `Passengers/Seat番号` へ書く。`read()` はそれを復元待ちのマップへ読み込む。[C2]

座席への搭乗は `addSittingPassenger()` による実体への乗車とUUID→座席番号の登録であり、`removePassenger()` は座席対応を削除する。`Carriage.serialize()` は車両実体側と内側のContraption側から `Passengers` を除去しているため、個別のNBTに同名キーがあることだけで、最終保存全体の内容は判断できない。[C2,C3]

### 3.3 プレイヤー向けの特別な復元経路

`dismountPlayer(..., capture=true)` は `PlayerPassenger` キーにプレイヤーUUIDを保存する。`updatePassengerLoadout()` はこのキーがあればサーバーの現在のプレイヤー一覧を検索し、取得できた同一ディメンションのプレイヤーを座席へ乗せる。`capture=false` は単に降車させる。車両実体の退避・削除では `portal` 引数がこのcaptureへ渡る。[C2]

したがって、ポータル等の車両退避のための復元機構と、通常終了後の再接続を同じものとして扱うことはできない。

### 3.4 条件付きで確認できる問題候補

`updatePassengerLoadout()` の712–736行では、`PlayerPassenger` に対応するオンラインプレイヤーが見つからず `passenger == null` であっても、その座席番号を `loadedPassengers` に追加し、後で `serialisedPassengers` から削除する経路がある。座席範囲外等の先行 `continue` や、取得済みプレイヤーが別ディメンションの場合は別経路である。[C2]

**仮説**：再開時にこの復元候補が存在し、プレイヤーの登録前にその経路が実行されるなら、後から参加したプレイヤーへ再試行する候補が残らない可能性がある。ただし、通常の終了で `PlayerPassenger` が保存されるか、どちらが先に読み込まれるかは未確認であり、今回の現象の確定原因ではない。[再調査:実機]

## 4. 現行CATとの関係 [再調査:CAT]

整理3.md第11.15節は、保存前に有効なATOが必要情報を再確認して再開すること、手動操縦担当は自動復元しないこと、担当不在の保存Pを無人実行しないことを定める。[D1]

このため、以下を独立した状態として扱う必要がある。

| 状態 | 復元で検討する意味 |
|---|---|
| 乗客が座席に座っている | プレイヤーを対応する座席へ乗せる |
| プレイヤーが運転手である | 権限・使用台・キー等を検証する。着席だけでは与えない |
| 列車が走行を再開できる | ATO／手動・保安・保持・経路の既存規則で決める |
| プレイヤーが未接続である | 座席の予約・待機・解除をどうするかは新たな判断 |

「乗客を復元するため全列車を止める」「座席を復元したので保存Pを再実行する」は、いずれも今回の調査から導かれる既決定ではない。

## 5. 修正方式を選ぶための考察 [再調査:CAT]

以下は実装案の比較であり、採用案ではない。

| 候補 | 得られること | Minecraftで必要な兼ね合い |
|---|---|---|
| プレイヤーに前回座席の参照を保存し、参加後に照合 | 参加時点を起点に再試行できる | 列車・車両・座席の恒久識別、消失・別人占有・期限・取消が必要 |
| 列車側に復元待ち乗客を保持 | 列車の現在位置と座席状態を基準にできる | 未接続者の情報をいつ消すか、読込不能列車をどう探すか、保存の重複回避 |
| 位置だけ車内へ戻す | 着席できない場合の候補 | 床・衝突・車体回転を再確認しないと落下や壁内配置が起こり得る |
| ATOの発車条件として乗客確認を加える | 発車前なら取り残しを減らせる候補 | 走行中の再接続を解決しない。多人数運行を一人の不在で止めるかは別判断 |

編成変更に対応する場合、`TrainId + CarriageIndex + SeatIndex` をそのまま永久IDとするのは避けて検討する。Createの車両実体は列車UUIDと配列上の車両番号で対応付けられるが、CAT独自連結・分離でその番号が同じ車両を指し続ける保証にはならない。[C4,D1]

多人数では、再接続した人のため既に座っている別プレイヤーを自動で降ろすか、復元を断念するかも必要になる。復元要求はサーバーが座席存在・空き・ディメンションを検証する方式が比較候補である。

## 6. 原因を絞る追加確認 [再調査:実機]

最初の比較候補は、同一の小さな列車で次の2ケースとする。ユーザー報告は受領済みだが、以下の条件を統制した追試は未実施。

1. 単独プレイで、標準座席へ着席し、時刻表を動かさず停車状態で通常保存終了→再開。
2. 同じ構成・座席で時刻表運転中に通常保存終了→再開。

観測項目は、終了前／再開後の座席・位置、列車UUIDと座席対応、保存中の `Passengers`／`PlayerPassenger`、プレイヤー登録と `updatePassengerLoadout()` の順序。次にEssentialでホスト本人と参加者、ホスト終了と参加者のみ切断を分ける。ゲーム内で専用ログを取る実装は今回していない。

追加で必要な資料は、実行版一覧と再現手順、必要時のみ関連ログ・複製セーブの対象NBTである。Minecraft／Forgeの終了処理まで確定する場合は、当該版のローカルで参照可能な対応ソースが必要。Essentialの責任と判定する根拠は現時点でない。
