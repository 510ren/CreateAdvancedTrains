# 13. 乗車時の視点移動と車内移動の調査

調査日：2026-10-22（日本時間）  
対象：Minecraft 1.20.1／提供されたCreate 6.0.8ソース、関連MODの作者公開説明、整理3.mdの2026-10-21保存版。  
検証：ソースの静的確認と公開資料の確認。ゲーム起動、操作感・同期・衝突の実測、CAT実装は行っていない。

## 1. 要点と読み分け

Create 6.0.8には、着席者を構造物の回転へ追従させる処理と、歩行者を移動構造物へ衝突させる処理が既にある。「車内移動を改善する」という要求は、この二つと、カメラ演出・クリック対象・車間通路を分けて評価する必要がある。標準処理の存在は、任意の列車形状で快適に移動できる証明ではない。[C1–C4]

- **事実**：今回読んだソースや作者資料で確認した事項。
- **考察／候補**：上の事実から導く設計上の比較。CATの承認済み仕様ではない。
- **不明**：提供資料や静的確認では判定できない事項。
- **[再調査:CAT]**：CATの対象・責任分担・保存／操作仕様が変われば再照合する。
- **[再調査:依存版]**：Createや対象アドオンの版が変われば該当コード・説明を再確認する。
- **[再調査:実機]**：実動作・性能・操作感の確認が残る。調査済みを意味しない。

## 2. 確認できた事実

### 2.1 着席時の方向追従 [再調査:依存版]

`ContraptionPlayerPassengerRotation` はクライアント設定 `rotateWhenSeated` を読み、プレイヤーが `AbstractContraptionEntity` に乗っている場合に動作する。車両では補間されたyaw／pitchを取得し、前フレームとの差をプレイヤーの向きへ加える。後ろ向き・横向きの場合はpitch差を反転または抑制する分岐がある。乗る実体が変わると比較用の前回角度を更新する。[C1]

したがって、標準Createでも「着席者が曲線で向きを変える」機構は存在する。一方、このクラスは非着席者を対象にせず、ロールの独立適用もここにはない。列車全体のすべてのカメラ処理がこのクラスだけで完結するとは断定しない。[C1]

### 2.2 座席と歩行は別の処理 [再調査:依存版]

`AbstractContraptionEntity.addSittingPassenger()` は実際の乗車関係を作り、サーバー側のUUID→座席番号対応を更新・送信する。座席クリックでは別プレイヤーの着席を確認し、降車時には対応を削除して降車位置の情報を記録する。ローカル座標とワールド座標の変換メソッドも持つ。[C2]

`ContraptionCollider.collideEntities()` は構造物に対する相対運動とローカル座標系を使い、回転した箱とブロック由来の衝突形状を評価する。クライアント自身・別プレイヤー・サーバー上のプレイヤーで処理経路を分け、補正や接触を扱う。これは通常の着席マッピングとは異なる経路である。[C3]

**ここから言えること**：表示モデル、当たり判定、着席、歩行、クリックを一つ直しても、残りの成立は保証できない。特にRTM等の見た目だけを追加する場合、床・壁・座席の機能定義を別に確認する必要がある。整理3.md第13.12節も同じ区別を残している。[C2,C3,D1]

### 2.3 カメラの回転と距離も別 [再調査:依存版]

Createの `ClientEvents.onCameraSetup()` はyaw／pitchアニメーションをカメライベントへ反映する。`CameraMixin` はカメラの最大ズーム距離の引数へ倍率を掛ける。この二つは、歩行中の床への追従や座席の保存そのものを解決する機能ではない。[C4]

### 2.4 関連MODで確認できた範囲 [再調査:依存版]

Create: Train Perspectiveの作者説明は、列車へのカメラ追従にlean／rollを加えること、Create標準の `Rotate when seated` と競合するためv1.1.0以降では設定を自動処理すること、立っている場合の動作が実験的であることを記している。Minecraft 1.20.1用v1.1.1はCreate 0.5／6対応との説明があり、クライアント用である。[W1]

これは**作者の公開説明**である。対象ソースは未提供のため、CATとの二重回転防止、歩行時の安全性、具体的な接続箇所、厳密なCreate 6.0.8との併用動作は未検証。視点MODを導入すれば車間通路や床の衝突も直るとは判断しない。

## 3. 現行CATとの照合 [再調査:CAT]

整理3.md第11.2節は、通常の視点操作とHUD用カーソルを切り替え、カーソル操作中は視点を固定し、復帰時に向きが飛ばない方針。第11.16節は、実速度・停止位置と車体の見た目の揺れを分離し、HUDを固定する方針である。[D1]

このため検討対象は少なくとも次の四つに分かれる。

| 層 | 目的 | 他の層へ自動的に広げないこと |
|---|---|---|
| プレイヤー位置・衝突 | 床上を移動し、壁や通路を扱う | カメラを動かしただけで位置を動かさない |
| 座席・乗降 | 座席を識別し乗車関係を作る | 着席を操縦権取得と同一にしない |
| 視点・車体表現 | 向きの追従、傾き、揺れを見せる | 演出で実速度・停止位置を変えない |
| 入力・HUD | 視点、カーソル、運転、歩行を振り分ける | GUIクリックを車内ブロック操作へ漏らさない |

## 4. Minecraftで再現する上での考察 [再調査:CAT]

以下は未承認の比較案である。

1. **改善の基準を分ける。** 「曲線で視線が外れる」「停車時に揺れる」「歩くと床から落ちる」「車間を渡れない」は原因候補が違う。各症状の再現条件を先に分ける方が、小さな修正で効果を確かめやすい。
2. **演出と照準の関係を決める。** 視覚だけロールさせても、ブロックをクリックする向きと一致しなければ操作しにくい。見た目、照準線、サーバーが認める操作距離をどう対応させるかは独立した設計課題。
3. **車間通路は車両ごとの座標をまたぐ。** 曲線や勾配では両車の相対姿勢が変わるため、見える幌を足すだけでは足場を保証しない。通路の衝突形状、乗り移る時点、狭い隙間を越える補助の有無を比較する。
4. **複数機能で同じ回転を足さない。** Create標準追従、CAT演出、外部視点MODを同時に用いるなら、各処理が受け持つ角度を整理する。設定を無断で固定するかどうかまで、作者MODの挙動からCATへ継承しない。
5. **操作感の設定は物理と分離できる候補。** 追従方向・揺れの強さ等をクライアント設定にしても、実際の位置・速度・乗車可否をクライアント任せにしない。固定HUD、低FPS、低TPS、通信遅延での読みやすさを確認する。

## 5. 不明点・追加資料と確認候補

- 不明：ユーザーが求める視点改善の具体的な症状と、立ち歩き／着席の優先度。現時点では両方を調査対象として分けた。
- 不明：Create 6.0.8で各症状が再現する線形・速度・車体構成、Essential環境での同期差。着席復元の報告をそのまま歩行不具合の証拠にしない。
- 追加ソース候補：外部視点MODとの具体的な連携を選ぶ場合のみ、Create: Train Perspectiveの採用対象版。現時点で導入を要求するものではない。
- [再調査:実機] 初回確認は、同じ車体で「曲線を着席通過」「同じ曲線を立ったまま通過」の2ケースが比較しやすい。その後、勾配接続、車間通路、HUD切替、低FPS／通信遅延を別条件として追加する。未実施。
