# 無操作監視EB装置とリセット操作の調査

- 対象：調査一覧の **6「無操作監視・EBリセット」**。
- 調査日：2026-10-22（日本時間）。
- 照合基準：[整理3.md](../../整理3.md)の2026-10-21保存版。
- 調査範囲：鉄道事業者の公開一次資料、現行CAT文書。実装・Minecraft試験は行っていない。

## 1. 要点

**無操作を検出して警報・非常ブレーキへ移るEB装置と、既に発動した非常ブレーキの復旧操作は別の機能として検討する必要がある。** 実鉄道には60秒の無操作で警報、さらに5秒の無応答で非常ブレーキという説明例がある。[R1,R2] この値をCATの既定値にすることや、全車種共通の規則とすることは今回決定していない。

CATには既に非常ブレーキの保持・復旧条件と無人ATOの方針がある。一方、無操作監視の対象・時間・有効操作・ATO中の扱いは未確定である。[C1] 既存の復旧ボタンへ機能を足すだけでは、両者の意味を整理できない。[再調査:CAT]

## 2. 記述区分・マーク

- **事実**：出典が支持する範囲。過去の発表を対象車両の現在の不具合と扱わない。
- **考察・提案**：CATで比較する未承認の候補。
- **不明**：今回確定できない事項。
- `[再調査:CAT]`：CATの運転・権限・保持・復旧等の仕様変更時に再照合。
- `[再調査:依存版]`：依存MODや入力・通信方式の変更時に確認。
- `[再調査:実機]`：Minecraft上で未検証の挙動・操作性。

## 3. 実鉄道で確認できたこと

### 3.1 監視対象と時間の具体例

JR西日本の2016年発表は、走行中の力行ノッチ、ブレーキ、気笛、EBリセットスイッチの操作を対象とし、60秒の無操作後にブザー、さらに5秒の無応答後に非常ブレーキをかける装置と説明する。[R1] JR東日本の2014年発表にも同じ時間と操作の説明がある。[R2]

これは当該発表が説明する装置の事実である。停車中の厳密な有効条件、速度閾値、押し続けた場合、非常ブレーキ成立後の解除手順、全形式のATO中の扱いは、これらの説明だけでは**不明**。一般名称が同じでも、その細部を一律に決めない。

### 3.2 自動制動を運転士操作と誤認した例

**事実**：JR東日本は2014年、同じノッチで力行中にATC／ATS-Pが自動制動した際などに、それを運転士の操作と認識してEB装置のタイマーをリセットする不具合を公表した。原因はTIMS内のソフトウェアで、変更による対策を示している。[R2]

**考察**：CATの「実効ノッチが変わった」という結果だけでは、人が操作した証拠にならない。ATO、TASC、信号、安全保持等による変化と、権限のある運転担当者の入力を区別する必要がある。この教訓はCATの制動曲線や画面配置が変わっても利用できる。

### 3.3 入力処理で監視が無効になった例

**事実**：JR西日本は2016年、改修後の一部車両で、特定の間隔のブレーキ入力によりカウントがリセットされ続ける不具合を公表した。[R1] これは当時の対象装置についての報告であり、現在の車両やCreateで同じ不具合があるという根拠ではない。

**考察**：単に「入力パケットを受信したらリセット」とすると、長押し再送、同じ値の同期、遅延した要求、運転権限のない利用者からの入力を取り違える余地がある。入力の受付・有効性・操作主体・時刻を分けて考える根拠となる。

## 4. 現在のCATとの照合 [再調査:CAT]

| 現在の記述 [C1] | 無操作監視を加える際の論点 |
|---|---|
| 第3.2節：操縦指令の検証・最終適用をINTEROSに集約 | EB装置側が直接速度や指定レバーを書き換える構造を前提にしない。 |
| 第6.1節：通常EBと要復旧EBを区別し、操縦担当の死亡・切断・距離超過等は特殊事象 | 無操作を新しい原因としてどう分類するかは未決定。切断検知を無操作タイマー満了まで待つ変更は、現在の条件からは導けない。 |
| 第6.2・6.3節：保持理由を個別管理し、手動復旧は完全停止・原因全解消・指定EB等を要求 | 警報中の応答で、別のEB原因や復旧待ちまで消さない。非常成立後の復旧条件を警報応答ボタンで迂回しない。 |
| 第6.4・7.16節：ATO側の復旧経路、無人ATOを認める | 全ATO列車へ運転士の定期操作を要求すると無人運転方針と衝突する。有人監視ATOを別モードにする案も未承認。 |
| 第11.4節：HUD終了と操縦担当の扱いを定義 | HUDを開いている人、運転担当、車掌、一般乗客を同一視しない。 |
| 第11.15節：再読込で非常理由を消さず、手動担当を自動復元しない | 再読込でタイマー・警報・復旧待ちをどう復元するかと、運転権限の再取得は別に定義する。 |

現行文書中の「EB」は主に非常指令・保持・復旧を指す。今回の追加候補である無操作監視を、同じ略称があることだけで実装済み・採用済みと扱わない。

## 5. CATで検討すること・Minecraftの兼ね合い（未承認） [再調査:CAT]

### 5.1 状態を分ける案

| 状態の候補 | 主な検討事項 |
|---|---|
| 監視対象外 | 停車中、無人ATO、運転担当なし等の扱いを個別に決める。「対象外」は既存のEB原因を解除する意味ではない。 |
| 監視中 | 最後の有効操作からの時間を数える。適用速度・モード・権限変更時の開始条件が必要。 |
| 警報中 | 音と表示で応答を求める。どの操作で警報を止め、計時を再開するかを定義する。 |
| 無応答による非常要求 | INTEROSへ独立の非常理由を渡す案。ノッチの見た目や指定位置を勝手に変更しない。 |
| 原因解消・復旧待ち | 応答があったことと、列車の非常復旧が成立したことを分ける。既存の複数原因管理と照合する。 |

これは状態整理の案であり、実車の完全な内部状態図ではない。特に「応答を原因解消と認める条件」「速度にかかわらず要復旧にするか」は未決定である。

### 5.2 何を有効な操作と認めるか

- 力行・ブレーキ・気笛・専用スイッチを候補にする。ドア操作、視点移動、HUDを開く、チャット入力まで対象を広げるかは別判断。
- **提案**：サーバーが認めた担当者からの新しい操作を基準とする。同じノッチ値の再送、他人の操作、ATO等の自動指令を一括でリセット要因にしない。
- 押下と長押し継続を区別する。常時押されたキーやキーリピートだけで永久に監視を回避できるか、アクセシビリティ上どの入力方法を用意するかを検討する。
- 無効な操作要求を「操作した意思」として認めるかは未決定。制御適用が拒否されたという結果だけで一律に有効／無効を決めず、原因ごとに整理する。

### 5.3 時間・通信・停止

**考察**：ワールドの時刻表示、シミュレーションの経過tick、現実の経過時間は異なる。睡眠や時刻変更で警報までの残り時間を飛ばす設計にはしない候補が考えられる。一方、低TPS時にゲーム進行に合わせて猶予を延ばすか、現実時間で数えるかはゲーム体験に関わる。

単独プレイの一時停止、Essentialのホスト画面を閉じた場合、サーバーが進行を続ける状態を区別する必要がある。今回、その各条件でゲームが実際に停止するかは検証していない。[再調査:実機]

境界時刻の入力と非常成立の優先順、通信遅延の扱い、再送・二重受信、切断、担当交代、使用台変更を定義する。クライアント申告の時刻だけで無制限に過去へ戻って非常成立を取り消す方式は、サーバーの状態管理と矛盾し得る。[再調査:依存版]

### 5.4 UIと他機能との重複

専用の警報応答操作を設ければ既存復旧ボタンと意味を分けやすい。同じ物理ボタンを状態によって使い分ける案もあるが、警報を止めたい操作が非常復旧や発車まで進めないことを画面・処理の両面で明確にする必要がある。

**考察**：EB装置の警報は運転担当への通知であり、旅客向けSpeakerControllerの案内音と役割が違う。現在のSpeakerControllerは一台一再生・割込みなし等の制約を持つため、警報を旅客案内と同じ再生経路へ追加する設計は別途検討が必要。[C1] 音だけでなく可視表示も候補にし、視点演出・画面倍率・音量設定による気付きやすさを確認する。

## 6. 不明点・追加確認

- CATで無操作監視を採用するか、手動運転のみか、有人ATOも対象か、サーバー設定／性能プロファイルのどちらで管理するかは未決定。
- E235系等、特定形式の完全な動作・閾値・復帰条件は取得していない。他事業者の公開時間だけで補わない。
- 提供Createの全入力経路へ無操作監視を接続できるかは今回の確定範囲外。実装へ進む段階では、対象入力MOD・版・担当管理方式に合わせて提供済みソースを確認する。[再調査:依存版]
- `[再調査:実機]` 最初の確認候補は、手動走行で無操作→警報→応答／無応答を比較する例と、同じ手動状態で安全装置の自動介入が計時をリセットしない例。以後、長押し、切断、低TPS、担当交代、保存再開、ATO切替を分ける。今回はすべて未実施。
- 特定車種へ忠実に合わせる必要がある場合は、対象形式・番台・運転方式と、入手可能な機器説明資料が有用。今回の基礎調査を完了するために非公開資料の提供を必須とはしない。
