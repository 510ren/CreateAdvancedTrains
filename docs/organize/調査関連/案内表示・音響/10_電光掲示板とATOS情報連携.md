# 10 電光掲示板とATOS情報連携の調査

- 対象：検討一覧の10「電光掲示板とATOS等の連携」。元の電光掲示板追加と、その追加に伴う各機能連携の精査を合わせて扱う。
- 調査日：2026-10-22（JST）。CAT照合基準：[整理3.md](../../整理3.md)の2026-10-21保存版。
- 対象：実在ATOSの公開説明、Create 6.0.8、提供Create Railways Navigator（CRN）0.10.0-C6 beta。
- 検証範囲：一次資料・ローカルソースの静的確認。Minecraft起動・表示試験・予測精度測定・CAT実装は未実施。

## 1. 要点・凡例

電光掲示板の追加には、画面だけでなく「どの運行情報を、いつの時点の情報として表示するか」を決める必要がある。実在ATOSは運行管理と案内を結び付けているが、現在のCATのATOSは自律的運行調整を行わない。表示連携のために実在ATOSの責任をCATのATOSへ一括移植する根拠はない。[R1,C1]

本書の**確認事実**は出典が支持する範囲、**考察／提案**は未承認の設計検討、**不明**は未確認事項である。

- **[再調査:CAT]**：CATの責任分担・時刻表・識別・運行仕様が変われば再照合。
- **[再調査:依存版]**：Create・CRN等の対象版変更時に再確認。
- **[再調査:実機]**：実際の表示・同期・予測・負荷の確認が残る。

## 2. 実鉄道側の確認事実

JR東日本はATOSの主要機能として、ダイヤの配信、指令による変更の駅への反映、自動進路制御、駅の放送・発車標による案内、保守作業管理を挙げる。案内機能はダイヤに基づく時刻・行先表示とダイヤ乱れへの対応を含む。[R1]

**限定**：この説明はシステムの役割を示すが、個別駅の画面構成、表示行を送るタイミング、秒単位の更新周期、到着予測アルゴリズム、全ての運休・番線変更規則までは示さない。これらは**不明**であり、一般的な駅で観察した表示をATOS全体の固定仕様とはしない。

**考察**：案内情報はダイヤと実際の運行状態の両方に関係する。ただし「表示が変わる」と「進路が設定される」は別の動作であり、表示器が進路許可や列車制御の正本を持つ必要はない。

## 3. Create・CRNで確認した情報の意味 [再調査:依存版]

### 3.1 Create標準の発車予測

`GlobalTrainDisplayData.refresh()`は、時刻表なし・時刻表一時停止・脱線・グラフなしの列車を除外し、`ScheduleRuntime.submitPredictions()`の結果を行先ごとに集約する。表示用の予測値は列車、残りtick、運行タイトル、行先を持つ。[L1]

`ScheduleRuntime`は走行所要時間を記録・更新し、現在の目的地までの距離、速度設定、過去の所要時間などから予測を組み立てる。停車時間推定では、条件列が`ScheduledDelay`だけで構成される経路を評価し、推定できない場合は`INVALID`とする処理がある。[L2]

`StationSummaryDisplaySource`は予測tickを「まもなく」または分・秒の文字に変換し、列車名・運行タイトル・フィルターから抽出した番線文字列等を表示する。[L3]

**考察**：これは「確定済みの絶対時刻ダイヤをそのまま表示する処理」と同一ではない。CATが力行・制動・保持・手動案内を独自管理する場合、標準の所要時間推定や列車抽出条件がCATの運行状態と合うかを別途評価する。標準表示から列車が消えたことを、CATの運休確定と読み替えない。

### 3.2 CRNの予定・予測・実績

提供CRNの版・依存宣言は0.10.0-C6 beta、Minecraft 1.20.1、Forge側Create 6.0.8である。配布JARとの同一性は未確認。[L4]

`StopSnapshot`には以下の別々の値がある。[L5]

| フィールド | 確認できた意味 | CATへ転用する際の注意 |
|---|---|---|
| `scheduledStation` | 時刻表側で期待していた駅 | 現に進入する駅とは別の可能性 |
| `station` | 実際に選んでいる駅 | 番線変更・代替駅との関係を要確認 |
| `scheduled` | 公開用の予定時刻 | 時刻表未確立時には予測で代用する設計を含む |
| `realtime` | 現時点の予測時刻 | 到着済み・発車済み実績とは同一でない |
| `previousActual` | コメント上は前回完了した停車機会の計測値 | 今回の列車の到着実績と取り違えない |

`StopSnapshot.of()`は`getPublishedScheduled()`、`getRealtime()`、`getPreviousRealtime()`をそれぞれ取得する。`StopTimings.getPublishedScheduled()`も確認した。したがって**フィールド名がscheduledであることだけを理由に、利用者が確定したダイヤ時刻だと扱えない**。[L5,L6]

`TrainSnapshot`は列車名・路線名・運行タイトル・行先・現在駅・次駅・運行状態・遅延理由を別々に保持する。表示行先はタイトル優先、表示列車名は路線名があればそれを使う。遅延の公開値は`max(0, maxDeviation - delayOffset)`であり、負の早着を同じ値で表現しない。[L7]

これらは提供CRNのデータモデルであり、CATの正式API・時刻体系・遅延定義として採用したものではない。CRNの全学習・予測処理や、計測から`previousActual`へ格納されるまでの全経路を独立検証したわけでもない。

## 4. 現行CATとの照合 [再調査:CAT]

整理3.mdでは次の境界がある。[C1]

| 現在の決定 | 掲示板に対する意味・未決項目 |
|---|---|
| INTEROSが列車情報の正本・情報共有を担当 | 表示器から車上状態を独自に変更しない方向と整合する |
| ATOSは常時稼働、要求伝達はINTEROS経由 | 掲示板を使うたびにATOS本体を起動する構造とはしない |
| ATOSは現段階で自律的な速度調整・ダイヤ調整をしない | 到着予測を表示することと、予測に合わせて運転を変えることを分離する |
| 共通進路管理が進入許可を確定 | 掲示板の「発車」「接近」は許可の代用にしない |
| 列車名と運行タイトルは別 | 種別・路線名・行先を全て列車名の文字列解析で済ませる前提を置かない |
| 時刻表の条件完了と発車可否は別 | 発車時刻を迎えても信号・保持等で出発できない場合の表示が必要 |

現在の文書は掲示板の完成仕様を持たない。情報の供給担当、表示対象駅と番線の結付け、運休・回送・通過・予定変更の意味は追加検討が必要である。

## 5. CATで検討する情報とMinecraftの兼ね合い [再調査:CAT]

### 5.1 データ項目の候補

以下は**提案**であり、全項目を初期必須とするものではない。

| 情報群 | 候補 | なぜ分けるか |
|---|---|---|
| 識別 | 列車ID、運行機会ID、駅ID、番線／停車目標ID | 同名列車・同名駅、環状運転の次周、連結分離を取り違えないため |
| 案内名称 | 種別、路線、行先、運行タイトル、駅の表示名 | 内部IDやCreateの駅名フィルターをそのまま利用者向け文字列にしないため |
| 時刻 | 予定、予測、実績、時間基準、確度・有効期限 | 未定を定刻と表示せず、予測を確定ダイヤとして保存しないため |
| 運行状態 | 停車／通過、接近、到着、出発、運休、変更、情報不明 | 「表示なし」と「運休」、「未読込」と「列車不存在」を区別するため |
| 更新情報 | スナップショット版、生成tick、変更理由 | 遅い応答で古い番線・行先へ巻き戻さないため |

予定時刻を持たない手動列車でも、列車の存在・次駅・通過予定を表示できる可能性はある。ただし、誰がそれらを確定するかが未定なら値を推測しない。未登録列車は限定された案内にする候補もある。

### 5.2 情報の流れの候補

**提案**：車上の確定情報はINTEROS、共通進路・駅設備の情報は担当機能、運行計画は確定済みの時刻表から収集し、案内用の読み取り専用情報へ整える。ATOS画面、駅掲示板、車内LCD、放送が同じ意味の情報を参照する。表示器そのものが各機能へ運転指示を出す構造とは分ける。

情報集約をATOSの内部機能とするか、独立した案内機能としてATOSも利用するかは未決定。共通データを用意することとCAT Libを作ることも同義ではない。

### 5.3 時間と予測

Minecraftのワールド時刻、経過tick、現実の時計は分ける必要がある。現在のCATは標準時刻条件を維持する方針であり、睡眠・時刻変更・低TPSの影響を受ける部分がある。[C1]

**考察**：定刻表示だけならダイヤと時間基準の整合が主課題だが、予測表示には走行性能、信号待ち、停車手順、進路変更、手動操作の不確実性が加わる。未知の待ち時間を0として足し合わせれば過度に早い予測になる。単一の分数を出すほか、「未定」「接近中」等に段階を分ける方式も比較対象になる。

### 5.4 行送り・変更・未読込

**提案**：発車標から列車を消す契機を、予定時刻到来・先頭発車・後尾退出・次運行へ移行のどれにするか明示する。ホーム内停車、通過列車、同時進入、番線変更、列車取消を別ケースにする。画面の行数を超える場合の優先順位も必要である。

駅・列車が未読込でも有効なサーバー情報を保持できる範囲は調べる必要がある。単に描画距離外という理由で運休へ変えたり、過去の接近情報を新規接近として再生したりしない設計が候補となる。

### 5.5 実機で残る確認 [再調査:実機]

長駅名・複数言語、同名駅、環状線の複数周、番線変更、時刻表差替え、手動への切替、低TPS、駅チャンクの読込停止、多数掲示板で確認する。予測精度は路線・運転方式・信号待ち条件別に測り、測定なしで「リアルタイムなので正確」としない。

## 6. 不明点・追加資料

- 特定の実在駅の表示優先順位・行送り・ATOS内部データ形式・到着予測式は不明。
- CATで番線・列車種別・運休・通過をどの単位で定義するかは未決定。
- CRNの予測・学習とCATの独自速度制御／手動案内を組み合わせた正しさは未検証。
- 特定の掲示板外観・案内挙動を再現する場合は、対象駅・表示例・変更時の観察が必要。公開資料の範囲を超える内部仕様は不明として残す。
- 提供CRNと異なる配布版へ接続する場合は、その対象版の提供ソースが必要。
