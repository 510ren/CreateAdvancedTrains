# 09 車内LCDと自由レイアウトの調査

- 対象：検討一覧の9「車内LCDの強化・自由なデザイン」。元の「LCDの強化」と「CATデータ対応・外部データ参照」は利用者の回答により同一項目。
- 調査日：2026-10-22（JST）。CATの照合基準は[整理3.md](../../整理3.md)の2026-10-21保存版。
- 対象資料：Create 6.0.8、提供されたCreate Railways Navigator（以下CRN）0.10.0-C6 betaのローカルソース、鉄道メーカーの公開技術資料。
- 検証範囲：文書・提供ソースの静的確認。Minecraft起動、描画・通信・性能測定、CATへの接続実装は実施していない。

## 1. 要点と読み方

表示する運行情報、画面の構成、画面を車体上へ描画する処理は、分けて検討できる。Createには文字列を表示先へ渡す仕組みがあり、CRNには列車内表示と表示型登録の実装がある。ただし、既存実装をそのまま使えばCATの任意データを読み、利用者が設定ファイルだけで自由なLCDを作れる、と確認できたわけではない。[L1–L5]

本書では次の区別を用いる。

- **確認事実**：明記した資料・ローカルソースで確認した範囲。
- **考察／提案**：確認事実からの設計上の推論。CATの承認済み仕様ではない。
- **不明**：情報不足または実動作未検証。都合のよい挙動で補完しない。
- **[再調査:CAT]**：CATのデータ・責任分担・表示要件が変われば再照合する箇所。
- **[再調査:依存版]**：Create・CRN等の対象版変更時に再確認する箇所。
- **[再調査:実機]**：実際のゲーム環境での確認が残る箇所。

## 2. 実鉄道側で確認できたこと

**確認事実**：日立の2021年の車内案内表示器の報告は、次停車駅・行先・列車種別などの案内、広告、異常時の情報提供を扱い、中央装置・端末装置・LCD表示器・車上通信装置からなる構成を示す。E235系の案内画面と広告画面の例も掲載されている。[R1]

**考察**：実車のハードウェア構成をMinecraftへそのまま移す必要はない。一方で、「車両の現在状態」「案内に用いる路線・駅の定義」「意匠・広告素材」が別の更新周期を持つ、という整理はCATでも有用である。広告用の動画や画像を扱えることは、運行情報を正しく取得できることの証拠にはならない。

特定車種の完全な画面遷移表、表示切替距離・時間、故障時表示、全言語の文言は本資料だけでは**不明**。本書は実車LCDの完全再現仕様ではない。

## 3. Create・CRNの確認事実 [再調査:依存版]

### 3.1 Create標準の表示連携

`DisplaySource`は`provideText()`で`List<MutableComponent>`を返し、`transferData()`で表示先の`acceptText()`へ渡す。フラップ表示には別の文字列受渡し経路がある。表示元の登録・検索、表示先の幅等を扱う`DisplayTargetStats`との接続も存在する。[L1]

この確認からいえるのは、**文字情報を表示元と表示先に分離して供給する既存の接続点があること**までである。任意画像、動画、自由な図形、車体上で動くLCD、CAT独自データの自動発見までを同じAPIが保証するわけではない。

### 3.2 CRNの版と表示型

提供CRNの`gradle.properties`は`mod_version=0.10.0-C6`、`release_channel=beta`、Minecraft 1.20.1、Forge側Create依存6.0.8、DragonLib beta-3.0.28を指定する。これは**提供ソースの構成**であり、配布JARとの同一性や起動成功の確認ではない。[L2]

`ModDisplayTypes`には旅客案内、列車行先、ホーム表示、発車標、静的文字などが登録される。`AdvancedDisplaysRegistry.register()`は表示カテゴリ・名前・設定オブジェクト・Javaのレンダラー・表示属性を受け取り、同じカテゴリ内の同名の二重登録を拒否する。[L3]

**確認できた範囲の結論**：プログラム側で表示型を追加する構造は存在する。任意のJSON・画像ファイルを置くだけで新しい描画ロジックまで追加できる汎用テンプレート機能は、この登録経路では確認できない。リポジトリ全体の不存在証明ではなく、確認した登録方式の限界である。

### 3.3 列車内表示の情報取得

`AdvancedDisplayBlockEntity.contraptionTick()`は車両構造物を識別し、列車UUIDを付けてサーバーへ表示データを要求する。応答の`TrainSnapshot`・`JourneySnapshot`を保持し、号車index・組立方向・逆向き走行の情報を反映する。表示状態・次停車駅・出口方向の差に応じてレイアウト更新とデータ更新を分ける。[L4]

要求処理は、列車の存在・利用可能性・ブラックリストを確認し、条件を満たさなければ列車・行程情報なしの応答を返す。[L5]

`TrainSnapshot`は列車名、路線、種別、現在の運行タイトル、行先、現在駅、次駅、編成数、位置・運行状態などを分離して持つ。`destinationText()`は運行タイトルが空でなければそれを優先し、空なら行先駅の表示名を使う。[L6]

**考察**：CAT側で運行タイトルを更新する場合、列車名だけを変更しても同じ表示にはならない。またCRNが読むスナップショットの供給元をCATの正本と整合させる必要がある。「CRN画面に文字が出る」と「CATの正しい運行状態を表示できる」は別の検証である。

## 4. 現行CATとの照合 [再調査:CAT]

整理3.md第3章では、列車情報の正本と共有をINTEROSが担当する。第8.20節では列車名と運行タイトルを分け、ATOで実行したタイトル更新を共有し、手動案内の進捗だけでタイトル命令を実行しない。Railways Navigatorとの運行情報互換を保つ方針がある一方、参照先・保存・更新方式は未確定である。[C1]

したがって次の内容は新たな採用判断になる。

| 論点 | 現時点で決められていない内容 |
|---|---|
| 表示データ | 次停車駅・通過駅・ドア側・号車・乗換等のうち何を正式に提供するか |
| 表示器の役割 | 案内専用か、タッチ操作・設定変更も認めるか |
| 車両との結付け | 列車／車両／設備の識別、連結分離後の所属変更、左右反転 |
| 自由度 | 色・文字位置だけか、図形・アニメーション・独自処理まで許すか |
| 連携方式 | CRNへCAT情報を渡すか、CAT表示器を作るか、共通データを両者が読むか |

## 5. Minecraftでの方式比較・考察 [再調査:CAT]

以下は**提案・比較**であり、実装済み機能や採用決定ではない。

| 方式候補 | 得られる自由度 | 制約・必要な判断 |
|---|---|---|
| CRN既存表示＋CATデータの接続 | 既存の旅客案内画面・設定を活用する | CRNの供給元とCAT状態をどう対応させるか。内部実装依存と版追従が必要 |
| CRNの表示型をプログラムで追加 | 独自の画面を既存表示器に載せる候補 | Javaレンダラーと依存版の管理が必要。利用者が画像を替えるだけの仕組みとは異なる |
| CATの宣言的な画面定義 | 文字・画像・線・条件表示などをファイルで構成する候補 | パーサー、座標・文字折返し・フォールバック、編集とプレビューを新たに設計する |
| スクリプト／HTML等の実行型 | 複雑なレイアウト・動作まで表現できる候補 | 実行時間、依存環境、操作範囲、配布、更新互換の負担が増える。現時点で必要とする根拠はない |

### 5.1 「外部データ」の三つの意味

1. **外観素材**：画像・フォント・配色等。リソースパック等に置く候補。運行情報の正本にはしない。
2. **ローカルの定義**：路線図、駅の読み、多言語名、レイアウト等。設定ファイルやデータパック等の候補。どちらを使うか、誰が編集するか、クライアントへの配布方法は未決定。
3. **他MOD／外部通信による動的データ**：CATまたは他MODのスナップショット、HTTPサービス等。単に表示を自由にしたいだけならHTTPは必須ではない。通信断時の有効期限・空欄・最終更新表示を決める必要がある。

データ形式を選ぶだけでは自由レイアウト機能にならない。読み込み、検証、同期、描画の実装が必要である。データパックを置けばクライアント表示へ自動同期される、という前提も採らない。

### 5.2 更新と描画を分ける

**提案**：同じ列車のLCDごとに運行データを再計算せず、列車単位の案内スナップショットを共有し、各画面は号車・向き・レイアウトだけを適用する。スクロール等の見た目はクライアントで補間し、駅到着等の確定イベントはサーバー情報で更新する。

この方式でも、折返し、連結、画面破壊、リソース再読み込み、列車のディメンション移動に伴う再結付けが必要になる。参照先が失われた画面に古い行先を無期限表示し続けるかどうかは明示する。

### 5.3 視認性・負荷 [再調査:実機]

日本語の長駅名、異体字、複数言語、画面の縦横比、乗車位置からの見え方、車体の揺れ、半透明材との描画順を確認する必要がある。画像の解像度を上げることと、離れた視点から読めることは別である。多数の画面による通信量・描画負荷・画像メモリ量は未測定。

確認ケースは、静止画面、長文スクロール、停車駅切替、折返し、情報欠落、長編成の多数画面を分ける。実機測定前に最大画面数や最小FPSを保証しない。

## 6. 不明点・追加資料

- CATの初期表示項目、自由度、外部データの意味・配布主体は未決定。
- 提供CRNの登録関数をCATから呼ぶ際の公式な互換保証、適切な初期化時期、DragonLibを含む全挙動は本調査では未確認。
- CAT制御下の手動列車をCRNの運行認識・時刻予測へ接続した動作は未検証。
- 実車の特定LCDを忠実に再現する場合は、対象車種・路線・画面遷移資料が必要。画像を参考にできても、内部ロジックを画像だけから確定しない。
- 外部アドオンの別版へ接続する場合は、その版のソース・依存版を利用者から提供してもらう。CRNは現在の提供ソースで調査できたため、同じものの再提供は不要。
