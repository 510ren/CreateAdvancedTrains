# 11 接近案内とSpeakerControllerの調査

- 対象：検討一覧の11「SpeakerControllerによるATOS接近音」。停車列車・通過列車を分ける案を扱う。
- 調査日：2026-10-22（JST）。CAT基準：[整理3.md](../../整理3.md)の2026-10-21保存版。
- 対象：JR東日本のATOS公開説明、カンノ製作所の列車接近システム一次資料、現行CATの音響・時刻表要件。
- 検証範囲：公開文書と現行要件の照合。実駅での観察、CAT音響実装、Minecraftでの再生・同期試験は行っていない。

## 1. 要点・凡例

停車列車と通過列車で接近案内を分け、列車情報と接近検知を組み合わせる実在製品は確認できた。ただし、その製品資料から「ATOSの特定音源が何メートル手前から、どの条件まで鳴るか」を確定することはできない。[R1,R2]

現行CATのSpeakerControllerは、発車メロディーの要求・再生・停止・終了通知を管理する構想で、一台一再生、割込みなし、停止確認まで手順を進めないという制約がある。接近案内の追加は、この制約と競合する場合を整理する必要がある。[C1]

- **確認事実**：出典で確認した限定範囲。**考察／提案**：未承認の選択肢。**不明**：確認できていない事項。
- **[再調査:CAT]**：CATの機能・責任分担・再生規則変更時に再照合。
- **[再調査:依存版]**：音響等の依存実装を採用し、その版が変わる場合に再確認。
- **[再調査:実機]**：ゲーム内の音、同期、重複・停止・未読込動作が未検証。

## 2. 実鉄道側の確認事実

### 2.1 ATOSとの関係

JR東日本のATOS説明は、ダイヤに基づく駅放送・発車標の案内と、運転整理変更の案内への反映を機能に含める。一方、この公開説明に個別の接近音の開始距離や停止条件は掲載されていない。[R1]

### 2.2 停車・通過の案内を分ける製品例

カンノ製作所の「列車接近システム」はTIDから列車番号を取得して停車／通過を判別し、両者の接近放送を分ける。ダイヤ・在線情報と発車標の連携、情報異常時の簡易放送も説明される。カタログには接近信号入力を含む構成例がある。[R2,R3]

**限定**：これは同社製品の仕様例であり、ATOSの全線区・全駅の仕様を説明した資料ではない。列車番号だけで停車／通過の意味が自明になるのではなく、その番号を運行計画と対応させる必要があるという点が読み取れる。具体的な照合テーブルや全判定ロジックは**不明**。

### 2.3 今回確認できなかったもの

次は一次資料で確定できていない。

- れんさんが想定する「ATOS接近音」の曲名・音源・駅・番線・時代。
- 音楽、チャイム、接近放送、通過警告のうちどこまでを含めるか。
- 停車用と通過用の具体的な音源差、音量差、繰返し回数。
- 接近検知点の配置基準、停車中の延長、途中停止・進路変更時の取消、後尾通過との関係。

これらを「実際は必ず○秒前／○m手前」と推測で埋めない。

## 3. 現行CATとの照合 [再調査:CAT]

### 3.1 既存のSpeakerController規則

整理3.md第13.10節の主な決定は次のとおり。[C1]

| 現在の決定 | 接近案内との接点 |
|---|---|
| スピーカーをControllerへ直接接続 | 番線やホームごとの放送範囲を結付ける候補になる |
| Controllerにワールド内一意の名前 | 対象指定に使えるが、名称だけでその場の列車・番線が決まるわけではない |
| 再生受付後は機器と再生IDへ結付ける | 古い停止通知が次の接近音を止める事故を防ぐために重要 |
| 停止までループ、指定時間または明示停止 | 一回再生して終える接近チャイムを追加するなら別の完了条件が必要か検討する |
| 一台一再生、割込み・重ね再生なし | 発車メロディー中に別列車が接近したとき、そのままでは新規音は使用中になる |
| 再生中は停止確認まで手順を先へ進めない | 駅の接近音を列車の停車後手順へ無条件に組み込めない |
| 異常終了と状態不明を区別 | 未読込・通知遅延を停止成功と決めつけない |

このため、音源を一つ追加するだけで停車・通過案内が完成するとはいえない。接近イベントの生成とControllerへの再生要求は別の課題である。

### 3.2 別の「接近音」との区別

第9.4節の**パターン接近音**は、速度が制動パターン上の許容速度へ接近したことを運転台周辺へ知らせる音であり、駅ホームへ列車が近づいた案内ではない。現在はINTEROSが列車単位でまとめ、使用中のマスコンから発音する決定である。[C2]

名称に「接近」が共通するだけで、SpeakerControllerへ統合したり同じ判定を使ったりしない。発車メロディー、警笛、運転台警告音もそれぞれ発音位置・権限・終了条件が異なる。[C1,C2]

## 4. CATで検討する責任分担 [再調査:CAT]

以下は**提案**。担当名・API・初期範囲を確定するものではない。

1. **案内対象の判断**：列車がどのホーム・進路へ接近しているか、そこで停車する計画か通過する計画かを判定する。
2. **案内イベントの管理**：同じ接近機会の重複を抑止し、運行計画変更・進路変更・後退による取消や再判定を行う。
3. **音の再生管理**：SpeakerControllerが音源、再生ID、開始・停止・終了結果を扱う。
4. **掲示板との共有**：停車／通過・番線・行先を音声と表示で食い違わせない。

実在ATOSが案内へ関わることは、この四つをCATのATOSへ全て実装する根拠ではない。現在のATOSはINTEROS経由の情報共有・プレイヤー要求伝達が中心であり、案内判定をどこへ置くかは未決定。[C3]

### 4.1 判定に必要な候補情報

| 情報 | 用途 | 欠けた場合の検討 |
|---|---|---|
| 列車と接近機会の識別 | 同一列車の再通知・別周回・折返しを区別 | 同じ列車IDだけで永久に通知済みにしない |
| 選択中の進路・対象ホーム・走行方向 | 隣接線や反対方向の誤案内を避ける | 直線距離だけで近いホームを選ばない |
| 停車／通過の計画と有効性 | 音・文言の選択 | 不明を通過や停車へ黙って変換しない |
| 経路上の距離・速度・停止状態 | 開始時機と途中停止の扱い | 距離計算の精度・先読み不足を表示情報と区別 |
| 先頭到達・停車成立・後尾退出等 | 音を止める契機 | どのイベントを使うかは案内種類ごとに決める |

手動列車に停車駅計画がない場合、速度が落ちたことだけを停車予定の証拠にしない。一般接近案内、運転者による事前指定、案内抑止などの候補を比較する。

## 5. 再生競合とMinecraftの兼ね合い [再調査:CAT]

### 5.1 発車メロディーと同時に必要になった場合

| 候補 | 利点 | 追加される負担・制約 |
|---|---|---|
| 別Controller・別放送系統にする | 現在の一台一再生規則を保ちやすい | 同じホームで両方が聞こえる場合の音量・聞き取りやすさを確認 |
| 同じControllerで順番待ち | 現在の排他に近い | 接近案内が列車通過後に遅れて鳴る危険。期限切れ取消が必要 |
| 優先度付きで割込み | 通過警告等を先に出せる候補 | 現在の割込みなし決定の変更。元の再生ID・手順・復帰位置・再開可否を再設計 |
| 複数再生チャンネル | 音の用途を分離しやすい | 一台一再生決定の変更。同時再生数、混音、音量、停止対象の複雑化 |

本書はどれも採用しない。実車製品に混音機能があることから、CATにも無制限混音が必要とは導けない。

### 5.2 時刻・同期・低TPS

**考察**：接近の判定tickと、クライアントで実際に音が始まる時刻は一致しない場合がある。再生開始の遅延を許す範囲、途中から読み込んだプレイヤーが先頭から再生するか現在位置へ追いつくか、停止指示の再送・重複処理を決める必要がある。

音声の実時間とサーバーtickの進み方が異なると、指定時間で止める音と、列車位置を見て止める音の挙動も異なる。低TPS時にどちらを優先するかは未決定。案内音が再生できないだけで無条件に非常制動する仕様は、現行の「音の異常だけで要復旧EBにしない」方針とも整合させる。[C1]

### 5.3 誤案内と負荷 [再調査:実機]

まず次のケースを分けて実動作を確認する必要がある。

- 停車列車と通過列車が同じホームへそれぞれ接近する。
- 進入直前に停車予定・番線が変更される、または信号で長時間停止する。
- 二列車が隣接番線へ同時に接近する。
- 発車メロディー再生中に通過列車が接近する。
- 先頭通過後も長編成の後尾がホーム付近に残る。
- Controllerやスピーカーの未読込・破壊・交換、途中参加、低TPSが発生する。

同期ズレ、重複音、音の止まり忘れ、聞き取りやすさ、同時接近時の負荷は未測定である。列車やホームが多い場合、各スピーカーが独立して全列車を探索する方式は重複計算を生む可能性があり、案内イベントの共有を検討できる。

## 6. 不明点・利用者へ確認したい内容

- 想定するATOS接近音の駅・番線・音源例。停車／通過の「音楽」だけか、音声案内も含むか。
- 実車の開始・終了条件をどこまで再現したいか。資料がない条件はCAT独自のゲーム向け規則として決める必要がある。
- 既存の発車メロディーと設備を共用したいか。設備共用の希望が競合方式の選択へ大きく影響する。
- 音源を利用者が用意するか、独自制作・差替え可能な素材を配布するか。対象音源の利用条件は未確認であり、録音を取得できることを配布可能の根拠にしない。

これらは今回の基礎調査を妨げるものではないが、再現範囲と採用方式の確定前に必要になる。
