# 踏切と列車保安装置の連携の調査

- 対象：調査一覧 **7「踏切機能」**。ATACS・ATS-Pとの関係、停車／通過、複数列車、Minecraftでの再現範囲を扱う。
- 調査日：2026-10-22（日本時間）。
- 範囲：JR東日本等の公開一次資料、手元のCreate 6.0.8ソース、整理3.md（2026-10-21版）。実装・ゲーム試験・実車仕様の完全な再現検証はしていない。
- 区分：**事実**は資料・コードの確認内容、**考察／提案**は未承認のCAT案、**不明**は未確認事項。
- マーク：`[再調査:CAT]`＝CAT仕様変更時に再照合、`[再調査:依存版]`＝対象版変更時に再確認、`[再調査:実機]`＝未実施のゲーム検証。

## 1. 調査結果の要点

**ATACSにも、ATS-Pを利用する踏切定時間制御にも、実在の連携事例がある。** 「ATS-Pは列車を止める装置だから踏切とは無関係」とは扱えない。ただし、すべてのATS-P設備が同一の踏切連携機能を持つことまでは今回確認していない。

CATでは「どちらの方式の列車でも警報・遮断できる」と「実鉄道と同様に踏切状態を受けて車上に防護パターンを作る」を別の対応段階として定義する必要がある。これは採用提案であり、互換仕様の決定ではない。

## 2. 実鉄道の確認済み事実

### 2.1 ATACS

JR東日本の2018年説明資料は、列車の位置・速度に基づく警報制御と、踏切の警報状態・支障に対応するパターン制御を説明している。図には到達時間算出、警報開始要求、踏切パターンと解除が区別されている。[R1]

2005年の評価論文では、車上で踏切動作の確認が得られるまで警報時間を確保する防護パターンを用いることが説明される。[R2] したがって「到達予測時刻になったので遮断完了とみなす」という単一タイマーの説明では、この仕組みを表せない。後半は資料からの設計上の推論。

これらは当時のATACSの設計・試験の説明であり、全導入線区の現在の設定値や装置構成を確認したものではない。

### 2.2 ATS-Pによる踏切定時間制御

JR東日本の2013年論文は、ATS-Pから得る停車／通過の選別情報により警報開始点を使い分ける仕組みを示す。車上に踏切防護パターンを作り、地上側の遮断完了情報を経て解除する。また、続行列車が先行列車の防護を誤解除したり、警報を早く終わらせたりする問題への対策を扱う。[R3]

JR西日本のD-TAS技術資料も、ATS-Pの機能を利用する定時間制御を既に一部導入していると記載する。同資料のD-TASへの追加開発内容を、そのままATS-Pの全方式の仕様と読み替えることはできない。[R4]

### 2.3 この調査で分かった責任の違い

上記を整理すると、少なくとも次は別々の情報・処理である。

| 層 | 実在資料で確認した内容 | CATへ持ち込む場合の区別（考察） |
|---|---|---|
| 警報開始の判断 | 到達予測、または停車／通過を使った開始点の選別 | 駅に停まる予定と、実際に踏切手前で止まれる状態を区別する。 |
| 踏切装置の動作・確認 | 警報状態・遮断完了などの情報 | 指令を送ったこと、アニメーション開始、遮断完了を同一扱いしない。 |
| 列車側の防護 | 踏切に対するパターンと解除 | 一つの踏切の解除で他の踏切や停止信号の制約を消さない。 |
| 複数列車の管理 | 続行列車を考慮した警報維持・解除対策 | 先行列車だけを追跡して最後尾通過を判定しない。 |

上表右列は本調査の推論であり、実車の詳細アルゴリズムを取得した意味ではない。[R1–R4]

## 3. Create 6.0.8の静的確認 [再調査:依存版]

1. `TrackObserver` は検知中フラグに相当するカウンターと、現在列車のUUIDを持つ。`keepAlive` でカウンターを8へ戻し、更新で減らし、非活性になると列車IDを消す。保存項目もある。[L1] 24–31、43–48、71–104行
2. `Train` は `occupiedObservers` 集合を持ち、列車前側の通過処理で追加し、後側で削除する処理がある。集合中のObserverへ必要条件下で `keepAlive` する。[L2] 185–249、452–453、507–509行
3. `SignalEdgeGroup` は列車集合と予約を区別して保持する。進路予約があることと、列車が実際に踏切へ近づいていることは同じ情報ではない。[L3] 21–72行。後半は情報構造からの考察。

**限界：** Observerの仕組みは検知候補になるが、踏切までの到達予測、遮断確認、複線の全列車管理、車上防護の完成機能ではない。今回の確認から「標準レッドストーンを接続すればATS-P／ATACS互換の踏切になる」とは判断できない。外部踏切アドオンの実装は未調査。

## 4. 現在のCATとの照合 [再調査:CAT]

- 第3.1節のATACS／ATS-PはCAT独自の併用方針。ATS-Pは車内信号を取得・制御利用しない方針で、踏切情報の取得経路は未規定。踏切用の地上情報・照査機能を足すかは別の仕様判断。[C1]
- 各機能の要求はINTEROSで検証・調整する。踏切由来の制動を追加しても、安全装置が列車速度を直接上書きする構成を当然の前提にしない。[C1] 第3.2節
- ATOSは現段階で自律的運行操作を行わない。踏切の必要情報をATOSが表示することと、ATOSを踏切の安全判断主体にすることは別。[C1] 第8.5節
- 地上信号の表示遅延と進路保護は区別済み。踏切警報・遮断にも同じ遅延を無条件で転用する決定はない。[C1] 第9.1節

## 5. CATで検討すること・Minecraftとの兼ね合い（未承認） [再調査:CAT]

| 論点 | 考察・候補 |
|---|---|
| 対応の段階 | A：装飾・レッドストーン制御、B：列車追跡による自動警報・遮断、C：遮断状態と列車防護の相互連携、というように範囲を分けて比較できる。AをC相当と表示しない。 |
| 基本データ | 踏切ID、対象線路・方向、列車ID、先頭／後尾位置、経路、速度、停車意図、実際の警報・遮断状態、取得時刻が候補。必須項目は方式ごとに絞る。 |
| 到達予測 | `距離÷現在速度` は等速という仮定に限る。停車状態からの発車・加速・勾配を含めた最早到達側の見積り、情報更新遅延を考える。速度0で予測不能なまま発車を許すかも要判断。 |
| 遮断完了 | 見た目の棒が下がったこと、サーバーで完了したこと、道路の障害物がなくなったことは別。装飾だけか、衝突判定を持つか、モブ・プレイヤー・車MODまで検知するかを決める。 |
| 複線・続行・逆走 | 列車／方向別の要求を保持し、全対象が解消して初めて解除する案。別線の列車、折返し、列車分離、途中消滅等でカウントを失わない方式を比較する。 |
| 停車／通過変更 | 時刻表を変更した、駅をスキップした、手動で通過した場合は、古い停車予定だけを根拠に警報を遅らせない。変更の反映と防護解除の順序が必要。 |
| 未読込と再開 | 警報指令を出せない／完了確認できない状態を、正常な開放状態と区別する。保存された遮断完了の有効性を再確認する。強制チャンク読込を必須化するかは未決定。 |
| 保安装置OFF | CAT列車の車上保護OFF時でも踏切は接近列車を追跡するか、標準Create列車にも動作させるかを明示する。踏切側だけで全列車の停止を保証しない。 |
| tickと現実時間 | 警報開始・遮断動作・列車移動を同じ時間軸で比較する。見た目のクライアント再生時間を安全条件の正本にしない。 |

## 6. 不明点・必要な資料・実機確認 [再調査:実機]

- 再現したい線区・年代における警報時間、遮断時間、解除条件、異常時取扱いの全仕様は不明。公開資料の事例数値をCATの既定値にしない。
- 「ATACS・ATS-P互換」が上記のどの段階を指すか、道路側の対象、警報音・遮断機の形態は今後の選択事項。
- 外部踏切MODと連携する場合は、その対象版ソース・利用条件・公開インターフェースが必要。外部コードは取得していない。
- 実機候補：単線通過、駅停車後発車、複線同時接近、続行、警報中の逆走・時刻表変更、未読込・再起動・踏切破壊。列車到達前の警報／遮断成立、後尾通過、他列車の要求残存を記録する。今回は未実施。
