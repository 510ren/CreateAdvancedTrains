# 信号機の名称と識別の調査

- 対象：調査一覧 **8「信号機の名称」**。用途名・個別名・内部識別子・方向・進路との関係を扱う。
- 調査日：2026-10-22（日本時間）。
- 範囲：公開一次資料、手元のCreate 6.0.8ソース、整理3.md（2026-10-21版）。ゲーム試験・CAT仕様の確定は行っていない。
- **事実／考察・提案／不明**を分離する。
- マーク：`[再調査:CAT]`＝CAT仕様変更時の再照合、`[再調査:依存版]`＝依存版変更時の再確認、`[再調査:実機]`＝未実施のゲーム検証。

## 1. 調査結果の要点

**「出発」「場内」「閉そく」は用途分類であり、「第○閉そく」「○番線出発」等の個別表示と、保存・参照に使う内部IDは分けて考える必要がある。** 名称を追加するだけなら表示機能として独立させやすいが、名称で操作対象や進路を選ぶと、改名・同名・方向・交換後の参照が仕様になる。

Createには線路上の点のUUIDがある一方、信号区間のUUIDは再構成時に新しく生成される。信号機名を区間UUIDへそのまま結び付ける案は、再構成を考慮せず採用できない。[L1][L3]

## 2. 実鉄道で確認できた事実

- 国土交通省の解釈基準は、場内を停車場へ入る列車、出発を停車場から出る列車、閉そくを閉そく区間へ入る列車に対する信号機として分類している。これらは灯数の分類ではない。[R1]
- 阪急電鉄の公式説明には、第一場内・第二場内という区分と、信号機の看板に出発・場内・数字を示して識別する例がある。同じ機器外観で異なる用途を持つという説明もある。[R2]
- 以上は用途と識別表示を別々に扱う根拠になる。ただし「第○閉そく」の番号を増やす方向、駅境界での番号の振り直し、上下線・複々線での一意性は、今回の資料で全国共通ルールとして確認していない。

## 3. Create 6.0.8の静的確認 [再調査:依存版]

| 確認した構造 | 根拠 | 意味・限界 |
|---|---|---|
| 線路上の点はUUID `id`、辺の位置、方向を判定する端点情報を持つ。通常NBT読込・書込で `Id` を保存する。 | [L1] 23–35、71–108行 | 表示名のために座標文字列だけを唯一のキーにする必要はない。ただし移設・複製・再作成での恒久性まで保証しない。 |
| `SignalBoundary` は両方向側のブロック位置、区間UUID、信号種類、状態を区別する。 | [L2] 34–46、155–166、278–319行 | 一つの境界と一つの物理灯器・方向の関係を確かめて名前を持たせる必要がある。 |
| `propagateSignalGroup` は新しいUUIDで信号区間を作る。 | [L3] 75–92行 | 区間IDは信号機の表示名・恒久IDの代用にできると即断しない。境界IDと区間IDも混同しない。 |
| 駅の `GlobalStation` は `name` を別フィールドとして持ち、NBTの `Name` に保存する。 | [L4] 40、61–64、88–90行 | IDと名前を分けるローカル実装例。駅と信号機の改名仕様が同じであることを意味しない。 |
| 確認した `SignalBoundary`・`SignalBlockEntity` の固有保存処理には駅の `Name` と同じ個別名保存項目がない。 | [L2] 299–319行、[L5] 68–80行 | CATの命名機能が標準信号へ自動的に備わっているとは判断できない。他MODの追加実装は未確認。 |

`TrackEdgePoint.read` はmigration時には通常読込を行わない。[L1] 89–96行。したがって「UUIDがNBT保存される」ことだけで線路編集・移設をまたぐ参照追従を証明したことにはならない。

## 4. 現在のCATとの照合 [再調査:CAT]

- 第11.7節では次の信号現示・線路沿い距離を表示するが、信号機の命名UI・名前参照の規則は確定していない。[C1]
- 第10.10・10.11節は共通進路管理と自動抽出した進路を基本とし、初期の手動進路登録・編集を含めない。**信号機に表示名を付けることを、進路を手動定義する機能の追加と同一視しない。**[C1]
- 第13.13節で誘導・入換信号を追加する方針がある。用途を自由文字列だけで判定すると、「入換」と名付けた通常信号の意味まで変える設計になるため、用途属性と名前の分離を検討する。[C1からの考察]
- SpeakerControllerのワールド内一意名・完全一致参照は、その機器の既決定である。信号機へ同じ規則を適用する承認ではない。[C1] 第13.10節

## 5. CATで検討すること・Minecraftとの兼ね合い（未承認） [再調査:CAT]

### 5.1 情報を分ける案

| 情報 | 役割の候補 | 例は仕様値ではない |
|---|---|---|
| 設備ID | 保存・操作・同期で対象を特定する | UUID等。コピー時は別設備かを判定。 |
| 表示名 | 利用者が読んで区別する | 「第3閉そく」「1番線出発」 |
| 用途属性 | 信号機の機能・選択可能現示を定義する | 通常／場内／出発／入換等。分類自体も要判断。 |
| 対象方向・線路 | どの列車が従う信号かを示す | 上下・接近側・対象辺。利用者の上り下り名とグラフ方向は別。 |
| 進路との関係 | どの許可・分岐先を表示するか | 共通進路管理への参照。名前だけから推測しない。 |

### 5.2 管理方式の比較

| 選択肢 | 利点 | 兼ね合い |
|---|---|---|
| 同名を許し、IDで参照 | 再現路線で駅ごとに同じ名称を使える | HUDで駅・路線・方向等の補足が必要。 |
| 路線／駅の範囲で名前を一意にする | 候補選択が分かりやすい | 路線・駅境界の定義、設備移動時の所属変更が必要。 |
| ワールド全体で一意にする | 名前参照が単純になる | 大規模路線やディメンション間で不自然な接頭辞を要求し得る。 |
| 名前は表示だけに使う | 改名で制御参照を壊しにくい | 人が名前で検索する機能と、機械のID参照を接続するUIが必要。 |

現段階ではどれも採用していない。

### 5.3 変更・保存・表示

- 改名は表示だけを変え、対象設備IDを維持する案と、名前参照を使う場合の再指定方式を比較する。改名で既存の許可・信号状態を解除する理由は別途必要。
- 撤去後に同名で再設置しても、古い設備への操作要求を新設備へ自動転送してよいとは限らない。名前一致と設備同一性を分ける。
- 構造物コピー、クリエイティブ複製、NBT複製、線路付替えでは、ID重複・方向反転・参照喪失を確認する。
- 長い日本語名、空欄、改行、装飾文字、同名候補の可読性、地上銘板の描画距離、HUD上の省略を検討する。内部キーに文字列を使うなら文字正規化の規則も必要。
- 多人数編集ではサーバー側の権限と変更順を確認する。表示名を知っていることを操作権限と同一視しない。

## 6. 不明点と追加検証 [再調査:実機]

- 対象路線の閉そく番号・名称標・上下線別の正式な命名規則は未取得。実車再現を優先する場合は、路線・区間・年代や参照写真を指定すると調査を絞れる。
- 線路再構成、信号移設・向き変更・複製、別ディメンションへのコピーで、Createの境界IDとCATの追加情報がどのように継承されるかは実機未確認。
- テスト候補：同名2基、改名中の列車接近、撤去後の同名再設置、逆方向併設、線路再接続、再起動、他人との同時編集。表示名と実際の対象が一致するかを記録する。
